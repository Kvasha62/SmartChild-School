## 6. Замечания

### NC-01 · Среднее · Правка 1: определения `pr21` и `pr22` останутся неиспользованными

**Доказательство.** Блок Правки 1 предлагает определить `pr18`, `pr19`, `pr20`, `pr21`, `pr22`. В предлагаемом тексте документа (Правки 2, 3, 4) используются только `pr18`, `pr19`, `pr20`. Проверено извлечением всех блоков `markdown` из плана: определены `{pr18, pr19, pr20, pr21, pr22}`, использованы `{pr15, pr16, pr17, pr18, pr19, pr20}`; разность — `{pr21, pr22}`.

Действующий документ соблюдает инвариант «множество использованных идентификаторов ссылок равно множеству определённых» (проверено: `issue4`, `pr3`, `pr7`—`pr17`). Инвариант проверялся в каждом предыдущем ревью. Реализация блока в предложенном виде инвариант **нарушит**.

Смягчающее обстоятельство: сам план называет минимальным набором `pr18`—`pr20` и помечает `pr21`, `pr22` желательными. То есть план внутренне противоречив: текст обосновывает одно, код блока приглашает скопировать другое.

**Вывод.** Дефект реализации, а не замысла. Устраняется двумя строками.

**Рекомендация.** Выбрать одно:
- **(а)** сократить блок Правки 1 до `pr18`, `pr19`, `pr20`;
- **(б)** добавить использование `pr21` и `pr22` — например, в строке таблицы этапов: «основание слияния — [PR #21][pr21]; запись о слиянии — [PR #22][pr22]». Вариант (б) предпочтительнее, если владелец хочет сохранить полную историю решения, и одновременно закрывает NC-02 частично.

**Критерий устранения.** После применения правок множества использованных и определённых идентификаторов ссылок совпадают.

### NC-02 · Среднее · Рекурсия не закрыта для таблицы этапов

**Доказательство.** PL-1 плана разрывает рекурсию для **перечня ревью** (строка 6). Таблица этапов §8 таким свойством не обладает: она перечисляет этапы по одному на изменение. После реализации таблица будет содержать 5 строк, последняя — для коммита `9f203708…`. Коммит, вносящий саму правку NR-01, описан не будет; неполнота того же типа возникнет немедленно.

**Вывод.** План устраняет NR-01 для прошедших событий, но не определяет порядок для своего собственного коммита.

**Рекомендация.** Явно указать в плане одно из двух:
- **(а)** реализующий PR добавляет шестую строку для своего коммита. Тогда на момент написания номер этого PR неизвестен (≥ 24); требуется формулировка без номера либо добавление ссылки после создания PR;
- **(б)** таблица этапов признаётся растущей хроникой: каждая содержательная правка добавляет строку. Это следует зафиксировать, иначе incompleteness будет восприниматься как дефект при каждой следующей проверке.

Вариант (б) согласуется с утверждённым принципом: в документе — краткая история, полные отчёты — в PR.

### NC-03 · Среднее · Последовательность: правило хранения против открытого L-02

**Доказательство.** Правка 2 формулирует правило как установленный факт: «Полные отчёты ревью и операционные отчёты хранятся в связанных PR». При этом §7 (строка 315) продолжает числить L-02 открытым вопросом с решающим «Владелец», а строка 322 — «После решения владельца вопросы переносятся в `docs/product-scope.md` либо закрываются ссылкой на решение». В составе Правок 1—5 обновление L-02 **не предлагается**; оно вынесено в шаг 4 последовательности (строка 81 плана).

**Вывод.** Между реализацией Правок 1—5 и шагом 4 документ будет утверждать в строке 6 то, что §7 числит нерешённым. Возникает внутреннее противоречие — той же природы, что и само NR-01.

**Рекомендация.** Либо включить обновление либо закрытие L-02 в тот же минимальный набор правок, либо выполнить шаг 4 **до** реализации Правок 1—5. Второе предпочтительнее: тогда строка 6 сможет сослаться на зафиксированное решение, а не утверждать практику без основания.

### NC-04 · Низкое · Смешение стилей ссылок в одном предложении

**Доказательство.** В Правке 2 одно предложение содержит две относительные файловые ссылки (`mvp-001-documentation-layout-proposal-review-response.md`, `…-followup.md`) и одну ссылку на PR (`[отчёте об исправлении TR-01][pr19]`).

**Вывод.** Смысл не искажается; единообразие оформления нарушено. Отчасти вынужденно: отчёт об исправлении TR-01 находится в PR, а не в `main`.

**Рекомендация.** Выдержать единый стиль в пределах абзаца — например, вынести ссылку на [PR #19][pr19] в отдельное предложение.

### NC-05 · Информационное · Опора на поведение платформы

**Доказательство.** План утверждает: «закрытые PR в GitHub сохраняются неограниченно», обосновывая рекомендацию CLOSE WITHOUT MERGE для [PR #19][pr19]—[PR #22][pr22]. Это практическое поведение платформы, а не задокументированная гарантия. Проверено: все восемь веток с отчётами существуют на `origin`; ветка PR #13 сохранена.

**Вывод.** Практически риск минимален; как гарантия утверждение не подтверждено документацией.

**Рекомендация.** Не опираться на это как на гарантию. Дополнительная мера: не удалять ветки закрываемых PR — это обеспечивает сохранность независимо от поведения `refs/pull/*`.
