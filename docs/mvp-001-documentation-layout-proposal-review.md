## 4. Существенные замечания

### RC-01 · Существенное · Раздел 2, абзац «Установлено», третий пункт

**Проблема.** Утверждение «За всю историю репозитория (**2 коммита**, все деревья) не существовало ни одного файла…» не соответствует фактическому объёму истории.

**Доказательство.** На проверяемом коммите: `git rev-list --count f0253e54…` → **11** коммитов, достижимых из `main`; `git rev-list --count e192275…` → **12**. История `main` содержит, в частности: `f48f5d0` (инициализация), `3f3422e` (BOOTSTRAP-001, PR #3), `224ad3e` (TECH-DESIGN-001), `3926265` (DOC-AUDIT-001), `028fa9f` (MVP-001, PR #7), `db2fb2b` (PR #8), `7196f75` (PR #10), `196c4f1` (PR #9), `3ebedd4` (PR #11), `280f903` (PR #12), `f0253e54` (PR #13).

Причина ошибки: на момент анализа локальный клон был мелким (`git rev-parse --is-shallow-repository` → `true`), поэтому автор видел только два коммита. Вывод сделан по неполной выборке, но сформулирован как утверждение о всей истории.

**Влияние.** Вывод, опирающийся на это утверждение, по существу верен — проверка по полной истории подтвердила отсутствие файлов с `review`/`report` в именах; единственное совпадение по `proposal` — сам проверяемый документ (см. RC-02). Однако документ, претендующий на точность в вопросах структуры репозитория, не должен содержать неверное основание вывода: при повторном использовании методики та же ошибка приведёт к неверным заключениям в других вопросах.

**Рекомендуемое действие.** Заменить «2 коммита» на фактическое число с указанием способа получения (`git rev-list --count <SHA>` после `git fetch --unshallow origin`) и добавить оговорку, что утверждение проверено по полной истории, а не по локальному клону. Дополнительно — указать в разделе 1, что анализ выполнен на раскрытом клоне.

**Критерий устранения.** Число коммитов в документе соответствует выводу `git rev-list --count` по полной истории; способ получения указан.

### RC-02 · Существенное · Раздел 2, абзац «Установлено», третий пункт

**Проблема.** Утверждение «не существовало ни одного файла с именем, содержащим `review`, `proposal`, `report`, `ревиз`, `предложен`, `отчёт`» становится ложным сразу после добавления самого этого документа: его имя — `docs/mvp-001-documentation-layout-proposal.md` — содержит «proposal».

**Доказательство.** Проверка по полной истории (все деревья всех коммитов, 12 коммитов) даёт ровно одно совпадение по указанным шаблонам: `docs/mvp-001-documentation-layout-proposal.md` — то есть сам проверяемый документ. Остальные одиннадцать файлов совпадений не дают. Утверждение верно для состояния **до** коммита `e192275…` и неверно для состояния **после** него.

**Влияние.** В слитом виде документ содержит самоопровергающееся утверждение. Читатель, сверивший его с содержимым `docs/`, обнаружит противоречие, что снижает доверие к остальным выводам раздела 2 и к рекомендациям, построенным на этом разделе.

**Рекомендуемое действие.** Переформулировать с явной границей во времени, например: «До добавления настоящего документа в истории репозитория не существовало файлов с именами, содержащими `review`, `report`, `ревиз`, `предложен`, `отчёт`; по шаблону `proposal` совпадений не было до появления настоящего файла».

**Критерий устранения.** Утверждение остаётся истинным при проверке по дереву коммита, в котором находится документ.

### RC-03 · Существенное · Раздел 8 «Не выполнено и не требовалось» и «Статус файла в Git»; раздел 1, строка «Рабочая ветка»

**Проблема.** Три утверждения описывают состояние до формирования коммита и после него становятся ложными.

**Доказательство.** Документ находится в коммите `e192275…`, который является вершиной PR #14. При этом документ утверждает:

| Утверждение в документе | Фактическое состояние |
| --- | --- |
| Раздел 8: «`git add`, `git commit`, `git push` и слияние не выполнялись» | коммит `e192275…` создан и отправлен; ветка существует на удалённом сервере |
| Раздел 8: «Статус файла в Git: новый **неотслеживаемый** файл в рабочем дереве ветки `arena/f2a336cf-smartchild-school`» | файл отслеживается, находится в коммите, входит в PR #14 |
| Раздел 1: «Рабочая ветка `arena/f2a336cf-smartchild-school`, HEAD `280f9032…`» | HEAD ветки на момент PR — `e192275…`; база — `f0253e54…`; `280f903…` — более раннее состояние, предшествующее приведению ветки к `main` |

**Влияние.** Документ, зафиксированный в коммите, утверждает, что коммит не создавался. Это прямое противоречие, которое любой проверяющий обнаружит немедленно, и оно затрагивает раздел, призванный подтвердить соблюдение ограничений задачи.

**Рекомендуемое действие.** Разделить в документе два состояния: состояние на момент анализа (допустимо сохранить как историческую справку с явной датой и пометкой) и состояние на момент PR. В разделе 8 заменить блок «Не выполнено и не требовалось» на описание фактически выполненных действий: один коммит, один добавленный файл, ветка приведена к `main`, PR открыт, слияние не выполнялось. В разделе 1 указать, что ветка перед коммитом приведена к `f0253e54…`.

**Критерий устранения.** Ни одно утверждение документа не противоречит состоянию коммита, в котором документ находится.

## 5. Прочие замечания (не блокируют принятие)

### C-01 · Раздел 5.1 против раздела 6

Рекомендуемый путь для предложения — `docs/mvp-001-starter-content-proposal.md`, тогда как в разделе 6 описан документ `MVP-001-starter-content-proposal-v2.md`. Неясно, распространяется ли рекомендация на версионированный документ и требует ли соглашение суффикса версии. **Рекомендация:** явно указать отношение рекомендуемого имени к версии 2 либо сформулировать правило для версионированных документов.

### C-02 · Раздел 5.1 против раздела 7

Раздел 5.1 рекомендует хранить открытые вопросы в `docs/product-scope.md` с обоснованием «Разделение реестра нежелательно», однако сам документ вводит отдельный реестр L-01—L-06. **Рекомендация:** либо явно оговорить статус L-01—L-06 как временного реестра, подлежащего переносу после решения владельца, либо сразу разместить их в `docs/product-scope.md`.

### C-03 · Раздел 3.1, строка с примером ADR

Пример `docs/decisions/3-short-title.md` использует `N=3`, что совпадает с существующим номером PR #3; по правилу ADR `N` — номер отдельного Issue. Риск неверного толкования шаблона. **Рекомендация:** использовать в примере нейтральный заполнитель, например `docs/decisions/<N>-short-title.md`.

### C-04 · Раздел 5.4

Документ обосновывает, что не является ADR и потому не требует отдельного Issue, — это верно по `docs/decisions/README.md`. Однако `CONTRIBUTING.md`, п. 1 раздела «Порядок выполнения задачи», ожидает Issue с целью, исходным состоянием, полным SHA, границами и критериями для каждой задачи; PR опирается на Issue #4, в границах которого задача размещения документации не заявлена. **Рекомендация:** либо оформить отдельный Issue, либо явно указать в документе, что задача выполняется в рамках Issue #4 с расширением объёма, согласованным владельцем.

### C-05 · Раздел 2, обзор истории

Из-за мелкого клона обзор пропустил релевантные для предмета задачи исторические задачи: `[DOC-AUDIT-001] Синхронизировать статусы документации` (`3926265`) и `[MVP-001] Зафиксировать согласованные в переписке решения в документации (#7)` (`028fa9f`). Для исследования структуры документации это существенный контекст. **Рекомендация:** после устранения RC-01 дополнить раздел 2 упоминанием этих задач.

## 7. Ограничения ревью

1. Ревью проведено по одному коммиту `e192275…` и не переносится автоматически на другие версии документа.
2. Содержимое проверяемого документа не изменялось; замечания сформулированы как рекомендации к исправлению.
3. Проверка истории выполнена после `git fetch --unshallow origin`; до раскрытия клона выводы о количестве коммитов были бы недостоверны — это же обстоятельство стало причиной RC-01.
4. Содержимое внешних артефактов Arena (утраченное предложение, отчёт ревью вне репозитория) не проверялось в рамках этого ревью: оно не входит в проверяемый коммит. Состояние этих файлов зафиксировано со слов раздела 6 и по результатам ранее выполненной проверки.
5. Оформление описания PR #14 проверено по составу, но не является предметом данного ревью.
6. Автоматические проверки репозитория не выполнялись: в проекте нет приложения, сборки, тестов и workflow CI (`CONTRIBUTING.md`, раздел «Проверки документационного PR»). Утверждений об успешном прохождении проверок настоящий отчёт не содержит.
