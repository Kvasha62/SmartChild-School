## 4. Выводы по NR-01 и NR-02

### NR-01 · Информационное, не блокирующее · Строки 4, 6, 349, 353

**Суть.** Документ изменён по четвёртому ревью ([PR #18][pr18], замечание TR-01), но нигде его не упоминает: поиск «PR #18», «третье ревью», «TR-01» по документу даёт ноль вхождений. Решение по TR-01 зафиксировано в [PR #19][pr19], которого в перечне строки 353 тоже нет.

**Создаёт ли NR-01 реальные проблемы для понимания истории документа — да, ограниченные.**

1. **Собственный аргумент документа обращается против него.** §4.4 обосновывает пробел именно тем, что «независимое ревью … не сохранено в репозитории: воспроизвести его содержание по репозитории невозможно». Теперь документ содержит правку, внесённую по ревью, которое в самом документе не прослеживается, — то есть воспроизводит проблему, которую сам описывает.
2. **Происхождение последней правки нечитаемо из документа.** Читатель merged-версии не узнает, почему §8 перечисляет три файла и что такое TR-01.
3. **Таблица этапов (строки 346—349) неполна.** Четыре строки описывают редакции 1—3, но не содержат строки для коммита `9f20370…` (исправление TR-01), хотя именно он является текущим HEAD.

**Степень проблемы — ограниченная**, по трём причинам:

- утверждения строк 6 и 353 **не ложны**: при перечислении ревью нет слов «только» или «всего», а фразу «решения по всем замечаниям» допустимо отнести к перечисленным ревью [PR #15][pr15]—[PR #17][pr17];
- информация **полностью восстановима** из репозитория: коммит `9f20370…` с сообщением об исправлении TR-01, [PR #18][pr18], [PR #19][pr19], [PR #20][pr20];
- замечание касается **метаданных и provenance**, а не содержательных выводов о структуре документации — ради которых документ и существует.

**Требуется ли исправление по правилам проекта — нет, прямо не требуется.** Ни `CONTRIBUTING.md`, ни `docs/coordination.md` не обязывают перечислять все ревью внутри рецензируемого документа. `CONTRIBUTING.md`, п. 8 требует актуального отчёта и повторной проверки для новых коммитов — это выполнено ([PR #19][pr19] и [PR #20][pr20] по SHA `9f20370…`).

**Рекомендация владельцу.** Выбрать один из двух вариантов:

- **(а)** принять PR #14 как есть, а NR-01 устранить отдельным PR после слияния — низкий риск, сохраняет текущий SHA валидным;
- **(б)** перед слиянием дополнить строки 4, 6, 349 и 353 упоминанием [PR #18][pr18], [PR #19][pr19] и [PR #20][pr20]. Потребует нового коммита и, следовательно, новой проверки по `CONTRIBUTING.md`, п. 8.

## 6. Ограничения проверки

### Какие автоматические проверки существуют

**Не существует ни одной.** В каталоге `.github/workflows` нет файлов; в проекте нет приложения, сборки и тестов; `CONTRIBUTING.md`, раздел «Проверки документационного PR», прямо предписывает не заявлять об успешном выполнении несуществующих проверок.

### Какие проверки фактически запускались

**Автоматические — ни одной.** Для SHA `9f20370…`, `a9f979a…`, `72d03bd…`: статусов коммита — 0, check runs — 0, ревью и одобрений — нет.

**Выполнены вручную:**

- `git diff --name-status`, `git diff --name-only`, `git diff --shortstat` — состав и объём PR;
- `git rev-list --count` для `280f903…`, `f0253e54…`, `e192275…` — объёмы истории;
- скан `git ls-tree -r --name-only` по всем деревьям с разложением по шести шаблонам;
- `git rev-parse --is-shallow-repository`, `git fetch --unshallow origin` — полнота истории;
- сверка множеств имён (`diff`), проверка ссылок и их целей по дереву коммита;
- `git diff --check`;
- проверка существования всех 15 внешних Issues/PR;
- сверка опубликованных блобов с объектами Git по sha256.

### Прочие ограничения

1. **Мелкий клон — инцидент настоящей проверки.** На старте `git rev-parse --is-shallow-repository` вернул `true`: рабочая среда была сброшена, история усечена. Первый прогон дал неверные объёмы (`rev-list --count f0253e54…` → 1 вместо 11). **Ложный результат обнаружен и устранён**: выполнен `git fetch --unshallow origin`, все проверки повторены на полной истории. Примечательно, что скан путей в мелком клоне дал те же числа (10/0, 11/1, 12/2, 13/3, 13/3), что и на полной истории, — это совпадение, а не доказательство: в усечённой выборке каждый добавленный файл увеличивал число путей ровно на единицу. Вывод сделан только по полной истории.
2. **Сброс рабочей копии.** Локальная ветка `arena/f2a336cf-smartchild-school` откатилась на `280f903…`; три файла документации стали неотслеживаемыми, пять файлов — изменёнными. Рабочая копия **не трогалась**. Удалённая ветка и PR #14 остались на `9f20370…`; содержимое локального неотслеживаемого файла байт-идентично опубликованному блобу (sha256 `42abff3c…990d6c`). Все выводы получены по `origin/*` и GitHub API, влияние инцидента на результаты исключено.
3. **Эндпоинт защиты ветки недоступен** (`403 Resource not accessible by integration`), поэтому отсутствие обязательных проверок подтверждено косвенно: нулевым числом статусов и check runs и отсутствием workflow CI.
