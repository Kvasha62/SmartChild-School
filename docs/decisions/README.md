# Записи решений

## Статус

Порядок предложен в [BOOTSTRAP-001]. В этом каталоге пока нет утверждённых
ADR. Наличие этого файла не означает утверждение bootstrap или принятие
продуктовых и архитектурных решений.

ADR (Architecture Decision Record) — запись значимого архитектурного или
продуктового решения с контекстом, альтернативами и основанием согласования.
Обычные задачи и технические отчёты остаются в Issues и PR.

## Порядок ведения

1. Для каждого нового ADR согласуйте отдельный Issue. GitHub назначает ему
   уникальный номер в репозитории; этот номер `N` становится ID решения
   `ADR-N` и частью имени `N-short-title.md`. Не вычисляйте «следующий» номер
   вручную. Для нескольких ADR создаются разные Issues, а не используется
   один номер общей задачи.
2. Перед созданием файла проверьте каталог и открытые PR по этому Issue.
   Один Issue соответствует одному ADR и одному активному PR с ним.
   Если предложение уже существует, согласуйте правки в нём, а не создавайте
   второй файл с тем же номером и другим названием. Ревьюер повторяет эту
   проверку перед принятием. Конфликт блокирует работу до уточнения.
3. Укажите задачу, контекст, требования, варианты и последствия. Отдельно
   пометьте неизвестные данные и предположения.
4. В PR укажите полный commit SHA версии для ревью. Решение владельца также
   должно явно относиться к полному SHA, а не только к имени ветки.
5. До явного решения владельца статус — `предложено`. Автор или агент не
   выставляет `принято` на основании своего ревью или успешных проверок.
6. После решения владельца статус и ссылка на доказательство согласования
   обновляются явно, без выдумывания или заднего датирования одобрения.
   Если запись обновлена новым коммитом, итоговый SHA также согласуется.
7. Не переписывайте принятое решение незаметно. Для существенной смены
   создайте новую запись с отдельным Issue, свяжите её с предыдущей и
   согласуйте замену.

Допустимые статусы: `предложено`, `принято`, `отклонено`, `заменено`.
Последние три требуют ссылки на явное решение владельца. Заменённая запись
сохраняется и ссылается на новую.

Уникальность номеров Issues обеспечивает GitHub. Соответствие «один Issue —
один ADR», уникальность именных алиасов и отсутствие параллельных PR
проверяются вручную; автоматического контроля в bootstrap нет.

## Шаблон будущей записи

Шаблон не содержит принятого решения. `N` заменяется фактическим номером
отдельного Issue для ADR. Остальные поля заполняются реальными значениями,
а не вымышленными ссылками или SHA.

```markdown
# ADR-N: Название

- Статус: предложено
- Дата предложения: YYYY-MM-DD
- Задача: ссылка на отдельный Issue #N
- Ревью: ссылка на PR и полный commit SHA проверяемой версии
- Решение владельца: отсутствует
- Заменяет / заменено: не применяется

## Контекст и требования

Что известно, какие ограничения утверждены, что остаётся гипотезой.

## Рассмотренные варианты

Варианты, их достоинства, ограничения и причины отклонения.

## Предлагаемое решение

Конкретное предложение, не выдаваемое за утверждённое решение.

## Последствия и проверка

Риски, стоимость изменений, способ проверить результат.

## Основание утверждения

Заполняется только после явного решения владельца: ссылка, дата и SHA,
к которому относится решение. До этого — «не утверждено».
```
