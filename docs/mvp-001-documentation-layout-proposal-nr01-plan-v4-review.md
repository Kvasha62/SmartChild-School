## 6. Оценка правила ПТ-3

**ПТ-3 не считается утверждённым.** Проверено по тексту плана:

- формулировка правила сопровождается пометкой «предложено, требует подтверждения владельца — §9, п. 5»;
- в таблице раздела 2 («Что утверждено владельцем 2026-10-21») ПТ-3 **отсутствует**; вхождения строки «ПТ-3 (утверждено» — 0;
- в §9 правило вынесено в перечень решений владельца (п. 5);
- в §8 (ограничения) прямо указано, что ПТ-3 предложено и требует подтверждения.

Содержательно правило не противоречит ПТ-2: дата означает момент последнего изменения, номер редакции — содержательную версию. Риск: без подтверждения владельца реализующий PR не должен обновлять дату; при отсутствии подтверждения применяется прежняя дата, а строка 4 остаётся без изменений либо с прежней датой — этот выбор требует отдельного указания владельца.

### NC-14 · Среднее · Проект закрытия строки L-02 в §7 утверждает решение владельца при статусе записи `предложено`

**Блокирующее для шага 1** (PR, который вносит запись и закрывает строку). Шаг 2 не блокирует, если шаг 1 выполнен корректно.

**Доказательство.** Текст §3.3, вносимый в том же PR, что и запись:

```markdown
**L-02 закрыт.** Решение владельца — вариант (а): полные независимые ревью и операционные отчёты хранятся в отдельных PR, при сохранении необходимых ссылок и краткой истории в основном документе. Запись решения — в [записях решений](decisions/README.md); строка сохранена в таблице выше как запись вопроса и решения по нему (статус записи — в `docs/decisions/README.md`).
```

По §3.1 тот же PR вносит запись со статусом **`предложено`**, а перевод в `принято` происходит только после явной фиксации владельцем по полному SHA. Следовательно в состоянии B основной документ утверждает «Решение владельца — вариант (а)», тогда как `docs/decisions/README.md` в том же состоянии утверждает «Статус: **предложено** — до явного решения владельца по полному SHA». Одновременно строка 6 в состоянии B по формулировке (iii) намеренно не утверждает принятия. Возникает рассогласование внутри одного документа и с реестром решений — того же типа, что NC-03 и NC-06.

Дополнительно: пояснение в §3.3 — «Оговорка про статус исключает утверждение о принятии до фиксации владельцем» — **неточно**: оговорка указывает, где записан статус, но не отменяет утверждение «Решение владельца — вариант (а)» в первом предложении.

**Вывод.** Версия 4 устранила проблему для строки 6, но не для текста закрытия строки в §7: симметричная правка не выполнена.

**Рекомендация.** Привести §3.3 к той же логике, что и §4.3:

- **(а)** заменить утверждение на нейтральное, истинное в состояниях B и C: «**L-02 закрыт.** Выбран вариант (а): полные независимые ревью и операционные отчёты хранятся в отдельных PR, при сохранении необходимых ссылок и краткой истории в основном документе. Запись решения — в файле `docs/decisions/README.md` (относительная ссылка); статус записи — `предложено` до явного решения владельца по полному SHA (после фиксации — `принято`)»;
- **(б)** либо распространить матрицу состояний A/B/C и на текст §3.3.

**Критерий устранения.** Текст закрытия строки и статус записи в состояниях B и C не содержат противоречащих друг другу утверждений; утверждение «решение владельца» появляется только в состоянии C.

### NC-13 · Низкое · Критерий определения состояния и переходы не зафиксированы

**Доказательство.**

1. Второй столбец матрицы §4.3.1 — статус записи в файле; первый — наименование состояния («решение владельца зафиксировано по полному SHA»). По `docs/decisions/README.md`, п. 6, после решения владельца текст статуса обновляется явно; план не указывает, в каком шаге это обновление происходит и что считать состоянием, если решение зафиксировано, а текст статуса ещё `предложено`.
2. §3.1, п. 2 допускает фиксацию решения владельцем в том же PR, то есть переход A → C минуя B; матрица и §4.1 этот переход не описывают.
3. Матрица содержит состояние A, но §4.1 рекомендует сначала шаг 1; план не указывает, допустимо ли применение правки 2 в состоянии A.

**Вывод.** Ошибка выбора формулировки безопасна (iii) истинна в B и C, (ii) истинна в A), но порядок действий для исполнителя остаётся неопределённым.

**Рекомендация.** Добавить в §4.3.1 один абзац: состояние определяется **фактом фиксации владельцем по полному SHA**, текстуальным отражением которого является статус записи; обновление статуса входит в шаг 1 либо выполняется сразу после фиксации; при расхождении применяется более осторожная формулировка; переход A → C допустим при фиксации до слияния; применение правки 2 в состоянии A допустимо только по отдельному решению владельца.

### NC-09 · Низкое · Утверждения в проекте записи и в §2 плана (унаследовано из версии 3)

**Требуется до шага 1**; шаг 2 не блокирует.

**Доказательство.** Проект записи (§3.2) утверждает: «ревью в PR #19—#25 — 0; комментарии — только `sourcery-ai[bot]`». Проверено: ревью в [PR #19][pr19]—[PR #28][pr28] — 0, комментарии — только от бота, комментариев владельца нет. Утверждение истинно для указанного диапазона, но диапазон **уже неполон**: существуют [PR #26][pr26], [PR #27][pr27], [PR #28][pr28]. Тот же диапазон повторён в §2 плана. Второе утверждение — «Варианты (б) и (в) не применяются» (см. §7) — является выводом из выбора варианта (а) и буквально владельцем не формулировалось.

**Рекомендация.** Заменить диапазон на формулировку без номеров; вторую формулировку подтвердить у владельца либо заменить на «применяется вариант (а)».

### NC-12 · Низкое · Нет сводного критерия готовности реализующего PR

**Желательно до шага 2**; формально не блокирует.

**Доказательство.** План содержит критерий устранения NC-01 (команда проверки инварианта ссылок в §4.2) и правила ПТ-1, ПТ-2, ПТ-3, но не содержит сводного перечня проверок после применения правок. Форма задачи в `docs/coordination.md` предусматривает разделы «Критерии готовности» и «План проверок».

**Рекомендация.** Добавить раздел «Критерии готовности»: инвариант ссылок; 5 строк таблицы этапов по 4 колонки; разрешимость относительных ссылок; отсутствие слова «всем» в строке 6; выбранная формулировка соответствует состоянию A/B/C; дата в строке 4 соответствует дате правки (при подтверждённом ПТ-3); отсутствие строки таблицы для собственного коммита правки (по ПТ-1).
