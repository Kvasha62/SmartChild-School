## 3. Инвентаризация направлений и структурных сущностей

### 3.1 Направления, заданные кодом

| Значение `direction` | Отображаемая подпись | Текущее подтверждённое использование | Не подтверждено |
| --- | --- | --- | --- |
| `scratch` | Scratch | Фильтр главной; допустимый выбор у LessonPage | Фактическое число материалов и целевая категория |
| `roblox` | Roblox | То же | То же |
| `python` | Python | То же; в репозитории есть один исходник урока Python | Импорт/публикация и полнота направления |
| `unity` | Unity | Фильтр главной; допустимый выбор у LessonPage | Фактическое число материалов и целевая категория |
| `oge` | ОГЭ | Фильтр главной; допустимый выбор у LessonPage | Фактическое число материалов и утверждённый тематический план |
| `ege` | ЕГЭ | Фильтр главной; допустимый выбор у LessonPage | Фактическое число материалов и утверждённый тематический план |

**Вывод для OQ-F1:** список направлений в интерфейсе не решает вопрос, являются ли они категориями верхнего уровня. Варианты для решения владельца:

- **A. Шесть направлений = шесть CategoryPage.** Проще всего сохранить понятную связь с текущим фильтром; требует подтверждения, что каждый материал относится ровно к одному направлению или что мультинаправленность будет отдельно смоделирована.
- **B. Категории имеют отдельную предметную семантику, а `direction` остаётся фильтром/метаданными.** Гибче для смешанных учебных разделов, но требует явного соответствия между направлениями и категориями.
- **C. Категории определяются только после инвентаризации содержимого.** Самый безопасный вариант, если реальные темы и материалы не укладываются в шесть отдельных ветвей.

**Рекомендация:** выбрать вариант только после получения экспорта страниц/тем и черновой таблицы соответствий. Не создавать шесть категорий автоматически по enum.

### 3.2 Темы и материалы

Подтверждённые свойства модели:

- `LessonTopic.title` ограничен 120 символами; есть уникальность `Lower(title)` и отдельный уникальный slug.
- `LessonPage.topic` — необязательный FK на одну тему, `on_delete=SET_NULL`.
- Одна тема может быть связана со многими уроками через обратную связь `lessons`.
- В `LessonPage` есть одно поле `direction`, один nullable `topic`, поисковые ключевые слова и теги.
- Теги и темы — разные сущности; наличие тега не является доказательством структурного размещения.

Невозможно достоверно определить из исходников:
- список текущих тем и их фактические slug;
- какие темы не используются и какие используются несколькими направлениями;
- какие уроки не имеют `topic_id`;
- реальные title/slug/live/status/parent у всех существующих страниц;
- дубли и коллизии публичных URL в текущей базе.

### 3.3 Черновая матрица инвентаризации данных

Эта матрица предназначена для заполнения после безопасного read-only экспорта из базы; пустые фактические значения не заменяются догадками.

| Сущность/случай | Что выгрузить | Правило классификации | Безопасное поведение до решения |
| --- | --- | --- | --- |
| Материал с одной темой и одним направлением | page ID, title, slug, URL, live, direction, topic ID/title/slug, parent ID | Кандидат на соответствие, но не автоматическое решение | Не перемещать до утверждения правила |
| Материал без темы (`topic_id IS NULL`) | Те же поля; явно отметить отсутствие темы | Структурное размещение не выводится из отсутствия темы | Составить отдельный список; не терять материал и не назначать тему по одному `direction` |
| Тема используется материалами разных направлений | topic ID/title/slug и все связанные page ID/direction | Решение о единой подкатегории, дублировании или cross-cutting | Не копировать и не выбирать направление автоматически |
| Тема без материалов | topic ID/title/slug/description, число связанных страниц | Возможно, неиспользуемая или подготовленная тема | Не удалять автоматически |
| Материал с неполными/неизвестными метаданными | page ID, title, slug, direction, topic, parent, live, URL | Требует редакционного решения | Оставить без перемещения, блокировать миграцию только по согласованному критерию |
| Одинаковые slug в разных предполагаемых уровнях | Все страницы с slug, page type, parent, URL | Проверить глобальную/локальную область уникальности и конфликты URL | Блокировать автоматическое создание/переименование при неразрешённой коллизии |

## 4. URL: подтверждённое и требующее проверки

### Подтверждено исходниками
- Шаблоны используют Wagtail `pageurl` для генерации ссылок.
- Сейчас `LessonPage` разрешено размещать непосредственно под `HomePage`.
- Шаблон урока ссылается на текущего родителя как на «Все материалы».
- На главной фильтрация использует query-параметры `?direction=` и `?q=`; при наличии этих параметров шаблон добавляет `noindex,follow`.
- В репозитории не обнаружен экспорт всех существующих URL страниц и не предоставлен доступ к production HTTP-ответам.

### Не считать подтверждённым
- Нельзя утверждать, что все текущие материалы имеют URL вида `/<slug>/`, пока это не проверено на данных конкретного сайта.
- Нельзя утверждать, что точное сохранение старых URL совместимо с новой иерархией на используемой версии Wagtail.
- Нельзя считать автоматическую смену URL или настройку 301 редиректов утверждённым решением владельца.

### Обязательная URL-инвентаризация перед миграцией
1. Из read-only Wagtail/PostgreSQL окружения выгрузить для каждой страницы: page ID, type, title, slug, parent ID, `url_path`, публичный URL, live/public/restriction state, дату публикации и revision metadata, если доступна.
2. Сохранить снимок «старый URL → page ID → материал» и отдельно отметить дубли, пустые/необычные slug, страницы с ограничением доступа и неопубликованные страницы.
3. Смоделировать целевые URL для каждого варианта и проверить конфликт URL старого материала с новым URL категории/подкатегории.
4. На отдельном прототипе Wagtail 7.4.3 проверить поведение `Page.url_path`, `pageurl`, разрешения маршрутов, перенаправлений и публикации после изменения родителя.
5. Подготовить таблицу «старый URL → целевой URL → ожидаемый HTTP-ответ» и проверить отсутствие циклов/цепочек редиректов.
6. Политику сохранения URL, смены URL и перенаправлений оставить на отдельное решение владельца (OQ-F6). После миграции проверить старые URL, новые URL, sitemap, canonical, query-URL и 404.

## 5. Вопросы владельцу и рекомендуемый порядок

### OQ-F1 — смысл шести направлений
**Требуется:** выбрать, соответствуют ли шесть направлений категориям верхнего уровня или остаются отдельной осью классификации.  
**Подготовка:** экспорт реальных материалов и черновая карта направлений.

### OQ-F5 — правила распределения тем и материалов
**Требуется:** определить правила для тем, материалов без темы и тем, используемых в нескольких направлениях.  
**Обязательные правила безопасности:**
- материал без `topic_id` не считается автоматически относящимся к подкатегории;
- `direction` само по себе не назначает FK `topic`;
- два применимых утверждённых правила, указывающие на разные подкатегории, — конфликт и остановка;
- два применимых правила, указывающие на одну подкатегорию, дают однозначное размещение без предпочтения одного правила;
- без применимого однозначного утверждённого правила материал остаётся неразмещённым, попадает в диагностический отчёт, а миграция не завершается успешно;
- тема, используемая несколькими направлениями, не дублируется и не привязывается к одному направлению без отдельного решения.

### OQ-F6 — публичные URL
**Требуется:** решить, обязательно ли сохранить старые публичные URL или допустимы новые URL с утверждённой политикой перенаправления.  
**Подготовка:** экспорт всех старых URL и технический прототип; до этого выбор не делать.

### OQ-F2, OQ-F3, OQ-F4, OQ-F7
- **OQ-F2:** определить лимит материалов на главной или подтвердить вывод всех опубликованных материалов; сортировка — новые к старым со стабильным tie-break.
- **OQ-F3:** отдельно утвердить индексацию категорий/подкатегорий, sitemap, canonical и `noindex` для query URL. Текущий `noindex,follow` на главной с фильтрами — наблюдение о коде, не автоматическое SEO-решение для новых страниц.
- **OQ-F4:** определить алфавитную или редакторскую сортировку подкатегорий.
- **OQ-F7:** до решения не удалять `direction`; сначала исследовать все зависимости в моделях, шаблонах, тестах, фильтрах, поиске, экспортах и контентном процессе.

## 6. План следующего read-only шага

1. Получить одобренный доступ к актуальной базе/экспорту Wagtail без секретов и без изменений.
2. Выгрузить фактические страницы, темы, связи и URL; сохранить число записей и контрольную дату снимка.
3. Сформировать отдельные списки: материалы без темы, темы без материалов, темы с несколькими направлениями, slug/URL-конфликты, неопубликованные и ограниченные страницы.
4. Подготовить таблицу соответствий-кандидатов для владельца; не запускать миграции и не сохранять изменения в базе.
5. Прототипировать URL поведение только в изолированной тестовой среде, не на production.
6. После решения владельца обновить документированные правила миграции. Только затем запросить отдельное разрешение на реализацию Э1.
