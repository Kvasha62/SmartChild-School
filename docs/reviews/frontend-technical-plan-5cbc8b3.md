## 4. Утверждённые требования и утверждённые решения (Issue #86 и комментарий владельца)

**Утверждённые продуктовые требования (Issue #86):**

1. **Главная:** последние опубликованные материалы из всех категорий, от новых к старым.
2. **Категория:** последние опубликованные материалы этой категории + полное дерево её подкатегорий.
3. **Страница материала/урока:** материал + полное дерево соответствующего учебного раздела.
4. Подкатегории — раскрываемые/сворачиваемые блоки; в раскрытом состоянии видны все уроки/материалы подкатегории.
5. На страницах материала дерево навигации показывает текущий материал, выделяет его, автоматически раскрывает содержащую его подкатегорию.
6. Несколько подкатегорий могут быть раскрыты одновременно.
7. Дерево доступно с клавиатуры, имеет корректные ARIA-состояния, удобно на мобильных устройствах.
8. **Вариант А:** статья и урок — единый тип материала.
9. Существующие направления Scratch, Roblox, Python, Unity, ОГЭ, ЕГЭ сохраняются; их точное размещение в новой иерархии — исследуется, не придумывается.
10. Ориентир ИА — общие принципы Metanit.com, без буквального копирования.

**Утверждённые решения (по комментарию владельца в Issue #86, 2026-10-28T13:59:08Z):**
- **Иерархия страниц утверждена:** `HomePage → CategoryPage → SubcategoryPage → LessonPage`.
  Подкатегории — реальные структурные страницы, не виртуальное дерево из snippets.
- **Единый тип материала утверждён:** статья = урок (вариант А), единый `LessonPage`.

Эти два пункта **не возвращаются в список открытых вопросов** (требование п. 6
задания на доработку). Открытые вопросы — в разделе 16.

### 5.2 URL и служба страниц (подтверждено)

- `HomePage(slug="smartchild-school")` создаётся в миграции `0001_initial.py`
  (L16—40) как дочерняя страница корня Wagtail; `Site.root_page` = HomePage.
  Поэтому корневой URL `/` обслуживает HomePage; URL урока — site-relative путь
  урока, например `/{slug-урока}/` (полный `url_path` содержит префикс
  `/smartchild-school/{slug}/`).
- Маршруты: `/sitemap.xml` (wagtail sitemaps), Wagtail-URLs, `/cms/`.
- **URL-модель Wagtail (основной факт для раздела 8):** URL страницы определяется
  её положением в дереве (`url_path` → site-relative `page.url`). Это подтверждается
  текущим кодом и тестами: например, тесты используют `lesson.url` и ожидают, что
  sitemap содержит `published.url`; redirect-тесты используют `home.url`. Следовательно,
  **перемещение страницы в дереве меняет её публичный URL** — это поведение Wagtail,
  а не следствие концепции «вложенности» как такой.

## 6. Утверждённая иерархия страниц и её следствия

Утверждённая структура:

```
HomePage (сайт-корень, каталог)
  └── CategoryPage          (категория; URL /{category-slug}/)
        └── SubcategoryPage  (подкатегория; URL /{category-slug}/{subcategory-slug}/)
              └── LessonPage  (материал; URL /{category-slug}/{subcategory-slug}/{lesson-slug}/)
```

Следствия (факты):

1. Подкатегории — страницы, а не сниппеты; материал принадлежит подкатегории
   **структурно** (родительская страница), а не только метаданными.
2. URL материала меняется с `/{slug}/` на `/{category}/{subcategory}/{slug}/` —
   следование URL-модели Wagtail (раздел 8).
3. `LessonPage.topic` (FK на сниппет) и `LessonPage.direction` (choices) либо
   заменяются структурными связями (родитель = SubcategoryPage; категория =
   предок CategoryPage), либо остаются как нормализованные метаданные с
   обязанностью согласованности (раздел 11).
4. Существующие материалы (дети HomePage) требуют перемещения в новую иерархию —
   миграция данных + контентное решение о размещении (раздел 9).

## 7. Варианты архитектуры (реализация утверждённой иерархии)

### Вариант A — рекомендуемый: полная page-tree, тема заменяется подкатегорией-страницей

- `CategoryPage` (новый тип страниц, дети HomePage): поле `direction`
  (choices = `DIRECTION_CHOICES`), SEO-поля.
- `SubcategoryPage` (новый тип страниц, дети CategoryPage): наследует тему
  (ранее — сниппет `LessonTopic`); поле для порядка (см. открытый вопрос OQ-F4);
  SEO-поля.
- `LessonPage` остаётся единственным типом материала (вариант А);
  `parent_page_types = ["school.SubcategoryPage"]`; `direction`/`topic` либо
  удаляются, либо остаются с валидацией согласованности (раздел 11).
- Сниппет `LessonTopic` заменяется страницами подкатегорий; существующие темы
  мигрируются в страницы подкатегорий (контентное решение — раздел 16).
- Дерево навигации — реальные страницы; рендеринг без N+1 (раздел 13).

### Вариант B — полная page-tree + сохранение сниппета `LessonTopic` как параллельной метаданной

- Подкатегории — страницы, но материал продолжает иметь `topic` FK; тема и
  подкатегория могут расходиться → дополнительная валидация и риск
  несогласованности. Не рекомендуется без веской причины (дублирование
  смысла «принадлежность к учебному разделу»).

### Вариант C — подкатегории как обычные страницы, но без отдельного типа

- Использовать одну модель страниц для категорий и подкатегорий с уровнем
  вложенности. Неудобно: разные панели, разные шаблоны, нет явной типизации
  в `subpage_types`. Не рекомендуется.

### Выбор

**Вариант A.** Он реализует утвержденную иерархию, избегает дублирования
принадлежности (раздел 11), даёт явную типизацию дерева и сохраняет единый тип
материала. URL-последствия анализируются отдельно (раздел 8).

## 8. Сохранение существующих URL материалов (исследуется отдельно)

### 8.1 Что подтверждено, а что требует прототипа/проверки

**Подтверждено (Wagtail 7.4.3; документировано и/или подтверждается текущим кодом и
тестами репозитория):**

- URL страницы определяется её позицией в дереве: `url_path` → site-relative
  `page.url` (подтверждается тестами: sitemap использует `page.url`, redirect-тесты
  используют `home.url`, slug-тесты проверяют `url_path`).
- Перемещение страницы меняет её URL (Wagtail `move()` пересчитывает `path`/
  `url_path`). Это фундаментальная особенность URL-модели Wagtail, а не
  «автоматическое следствие вложенности»: если бы материалы остались детьми
  HomePage, URL не изменились бы, но тогда иерархия бы не была утверждённой.
- `first_published_at` — поле страницы, зафиксированное при первой публикации;
  не зависит от URL (подтверждается publish-логикой в тестах).
- Redirects framework (`wagtail.contrib.redirects`, уже в `INSTALLED_APPS`) сопоставляет
  старый путь с целью; sitemap формируется из `page.url` опубликованных страниц.

**Требует прототипа/проверки (не выполнено в этой среде):**

- Поведение масштабного `move()` в data-миграции на Wagtail 7.4.3 + PostgreSQL 18.6:
  атомарность, сохранность истории revisions, обновление search-индекса
  (`wagtail.search` в `INSTALLED_APPS`), обработка страниц с restriction/
  view-restriction, выполнение во времени.
- Унификация slug среди братьев на уровне БД на 7.4.3 (валидация в формах
  гарантирована; форму DB-ограничения — проверить).
- Регенерация sitemap/redirect после bulk-move; поведение `page.url` для
  страниц с alias; кеш-последствия (WhiteNoise/static; HTML-кеширование сейчас
  не настраивается).
- Точное сохранение URL **несовместимо с утверждённой иерархией в стандартной
  URL-модели Wagtail** — это вывод из п. 1 выше, но каждый миграционный сценарий
  нужно подтвердить прототипом.

### 8.2 Варианты URL/маршрутизации с явными последствиями

**Вариант U1 — принять смену URL + редиректы (301) со старых URL материалов.**
- Старые URL `/{slug}/` работают через 301 на новые; поисковые системы
  переносят «вес» ссылки; canonical — новый URL.
- Последствия: canonical меняется, требуется политика редиректов и мониторинг
  404; старые URL не являются каноническими; нужно согласовать политику
  (TECH-DESIGN-001 §H: 301 только при явно согласованной политике).
- **Решение о редиректах — за владельцем** (не принимается этим отчётом).

**Вариант U2 — кастомная маршрутизация: обслуживать материалы на старых URL
(`/{slug}/`), сохраняя дерево для иерархии.**
- Методы: переопределение `get_url_parts`/URLconf, middleware, alias-страницы.
- Последствия: два URL на один материал (дублирование контента для SEO),
  сложности canonical/sitemap/redirect/кеша; ломается векторная модель URL
  Wagtail; высокая сложность поддержки. Не рекомендуется без сильной
  бизнес-причины.

**Вариант U3 — оставить материалы детьми HomePage (URL без изменения).**
- Тогда `LessonPage` не является дочерней страницей `SubcategoryPage` —
  **противоречит утверждённой иерархии**. Отклонён.

**Вариант U4 — alias-страницы (Wagtail alias).**
- Alias redirectит с альтернативного URL на канонический — эквивалентно U1
  с дополнительной механикой. Рассматривается как вариант реализации U1.

**Вывод.** Полноценная вложенность **не требует** смены URL как концепция, но в
стандартной URL-модели Wagtail перемещение материала в подкатегорию **меняет**
его публичный URL. Точное сохранение текущих URL материалов несовместимо с
утверждённой иерархией без дополнительных механизмов (U1/U2/U4), каждый с
явными последствиями. Редирект-политика — вопрос владельца (раздел 16).

### 8.3 Пошаговый переходный сценарий URL (применяем по решению владельца)

Реализация U1 (смена URL + редиректы) — **решение о редиректах за владельцем**
(OQ-F6). Ниже — технический план шага, не решение.

1. **Инвентаризация старых URL до миграции.** Сбор полного списка старых URL всех
   материалов (`page.url` на текущем state, т.е. дети HomePage) в отчёт миграции.
   Проверка соответствия: каждый старый URL однозначно сопоставляется с
   конкретным материалом (URL уникальны в дереве); каждый материал охвачен
   ровно один раз.
2. **Конфликт старого URL материала и нового URL категории.** Если существующий
   материал `/python/` (детский HomePage) имеет старый URL `/python/`, а после
   миграции создаётся категория с URL `/python/` — конфликт. Защита порядком и
   временными slugs (алгоритм — раздел 10.1): категории создаются с slug, не
   конфликтующим с существующим top-level slugом материалов (например,
   `python-category`); материалы перемещаются в подкатегории; затем категории
   переименовываются в целевые slug (URL категории меняется; redirect
   старый→новый). **Перед каждым созданием/перемещением/переименованием —
   проверка актуального состояния и целевого slug; перед снятием временных slug —
   повторная проверка уникальности всех целевых slug и URL;** любая неразрешённая
   коллизия останавливает миграцию с диагностикой. Если конфликт остаётся —
   фиксируется в отчёте и решается политикой slug (раздел 9).
3. **Создание redirect-записей.** Для каждого старого URL материала — redirect
   entry → новый URL (или по политике владельца). Проверки:
   - **нет циклических redirects** (A→B и B→A);
   - **нет цепочек redirects** (A→B→C, когда можно A→C);
   - старый URL не совпадает с новым (redirect «на себя» — запрещено).
4. **Проверка 404 после перехода.** Все старые URL → 301 → новый URL (по
   политике); новые URL → 200; старые URL без redirect → 404 — фиксируется в
   отчёте; мониторинг 404 в течение периода после перехода (по решению
   владельца).
5. **Prototype на Wagtail 7.4.3.** Каждый шаг — техническая реализуемость, которую
   нужно подтвердить прототипом (bulk-move в data-миграции + redirects framework):
   **не выполнено в этой среде** (раздел 8.1).

## 9. Конфликты slug

### 9.1 Уровни конфликтов

- **Уровень siblings (один родитель):** Wagtail гарантирует уникальность slug
  среди страниц с одним родителем (проверка при сохранении; DB-форма —
  проверить на 7.4.3). Категория и материал с одним slug под одним родителем —
  конфликт.
- **Уровень URL (полный путь):** в дереве полные пути уникальны по построению
  (цепочка предков + уникальность slug среди братьев) — поэтому категория,
  подкатегория и материал с одинаковым slug в разных ветках **не конфликтуют**
  по URL (например, `/python/` и `/scratch/python/`).
- **Уровень перехода (миграция):** существующие материалы — дети HomePage;
  новые категории — тоже дети HomePage. Если существующий материал имеет
  slug, равный slug категории (например, материал `/python/` и категория
  `/python/`), на уровне siblings (родитель HomePage) и URL — конфликт. Нужна
  упорядоченность и временные slugs (алгоритм — раздел 10.1): категории создаются
  с slug, не конфликтующим с существующим top-level slugом материалов; материалы
  перемещаются в подкатегории; затем категории переименовываются в целевые slug;
  остаточные конфликты блокируют миграцию с диагностикой.

### 9.2 Политика разрешения (предложение, требует решения владельца для контента)

- **Однозначно рекомендуется:** миграция выполняет проверку конфликтов до
  применения; конфликты не решаются молча.
- Политика на случай конфликта (на выбор владельца):
  - (a) не применять конфликтующую страницу, зафиксировать в отчёте;
  - (b) автоматическое добавление суффикса (`-2`) — как `LessonTopic.save` уже делает
    для тем (models.py L128—146);
  - (c) контентное решение (переименование/объединение) — за владельцем.
  **Автоматические суффиксы и контентные переименования не вводятся без
  решения владельца** (алгоритм миграции, шаг 4): миграция при коллизии
  блокируется с диагностикой, а не переименовывает контент сама.
- **Тесты:** уникальность slug среди братьев; конфликт category-vs-material
  на top-level; два материала с одинаковым slug в одной подкатегории;
  behavior при выбранной политике.

## 10. Миграции и откат (защитные проверки)

### 10.1 Прямое применение (forward) — один выполнимый алгоритм

**Шаг 0. Схемные миграции.** `CreateModel CategoryPage`, `CreateModel SubcategoryPage`,
изменение `parent_page_types`/`subpage_types` (через `AlterField`/`AlterModelOptions`
или пересмотр моделей); `makemigrations --check` остаётся чистым.

**Шаг 1. Предварительная инвентаризация и проверки (до любых изменений):**
- Инвентаризация старых URL всех материалов (`page.url`, дети HomePage) — как в
  разделе 8.3: каждый старый URL однозначно сопоставлен с конкретным материалом;
  каждый материал охвачен ровно один раз. **Неполное сопоставление блокирует
  миграцию** (см. тестовую матрицу).
- **Полная инвентаризация slug всех затрагиваемых страниц:** существующие
  страницы (все дети HomePage: материалы и другие публичные страницы) и
  создаваемые миграцией объекты (страницы категорий, страницы подкатегорий,
  dashboard-страницы). Проверка: уникальность slug среди siblings (по каждому
  родителю) + конфликты полного URL (URL-path).
- Сравнить top-level slugы существующих материалов с планируемыми slugами
  категорий (DIRECTION_CHOICES, вопрос OQ-F1).
- Выявить материалы по трём случаям (раздел 11): (a) отсутствие `topic_id`;
  (b) фактический структурный родитель в исходном дереве (все материалы — дети
  HomePage, каталог); (c) возможность **однозначного** назначения целевой
  `SubcategoryPage` по правилу (тема → подкатегория по решению владельца,
  OQ-F5; направление → подкатегория по решению владельца, OQ-F1) — если правило
  неприменимо или неоднозначно — блокирующее условие (шаг 7).

**Шаг 2. Подготовка целевых страниц в порядке, не вызывающем конфликтов URL/slug:**
- **Перед каждым созданием проверять актуальное состояние и целевой slug**
  (уникальность среди siblings по родителю + полный URL).
- Создать страницы категорий с **уникальными slugами, не конфликтующими с
  существующим top-level slugом материалов** (например, материал `/python/`
  существует — категория создаётся с slug `python-category`; это временное
  название; переименование в целевой slug — шаг 4).
- Создать страницы подкатегорий под каждой категорией; slug проверяется на
  уникальность среди братьев под каждым родителем (Wagtail-форма; DB-форма —
  проверить на 7.4.3).
- Порядок **не решает конфликты автоматически**: остаточные конфликты (два
  материала с одинаковым slug в одной подкатегории; slug материала, равный
  slug целевой подкатегории) **блокируют миграцию с диагностикой** (шаг 3/6).

**Шаг 3. Перенос материалов — два разных решения (структурное размещение и
связь темы).**

**Операция A — структурное размещение:** определить целевую `SubcategoryPage`
для `LessonPage` по утверждённому правилу структурного размещения.
**Порядок проверки (конфликт выявляется до выбора правила); все исходы
определены явно:**
1. Определить **все применимые утверждённые правила**: «тема → подкатегория»
   (OQ-F5) и «направление → подкатегории» (OQ-F1).
2. Если оба правила применимы и указывают на **разные подкатегории** —
   диагностика и остановка миграции; **автоматический выбор запрещён** (решение
   о преобладании правила — за владельцем).
3. Если оба правила применимы и указывают на **одну и ту же подкатегорию** —
   результат **однозначен**: миграция использует эту подкатегорию **без
   предпочтения одного правила другому** (приоритет правил не назначается
   автоматически; нет конфликта и нет необходимости выбирать правило).
4. Если применимо **только одно** утверждённое правило и оно **однозначно**
   определяет подкатегорию — использовать его. Это включает два подслучая:
   применимо только правило «тема → подкатегории» — использовать его,
   существующая связь темы сохраняется; правило темы **неприменимо**, а
   утверждённое правило «направление → подкатегории» применимо **однозначно** —
   использовать правило направления (включая случай существующего `topic_id`
   без правила темы: структурное размещение выполняется по правилу направления,
   а существующий FK `topic` сохраняется **без произвольного изменения**).
5. Если нет применимого однозначного утверждённого правила — диагностика и
   блокировка до решения владельца.

Не вводить новых правил сопоставления и не решать за владельца, какое правило
должно преобладать при конфликте. Правило «тема → подкатегория» должно быть
**подтверждено владельцем**: соответствие темы и подкатегории не предполагается
без утверждённого правила.

**Операция B — связь темы:** определить, сохраняется или восстанавливается
`topic_id` на существующий `LessonTopic`. Это **отдельное решение** — оно не
подразумевается автоматически из операции A:
- если `topic_id` указывает на существующий `LessonTopic` — связь сохраняется
  (тема существует; восстановление не требуется);
- если `topic_id` отсутствует — **не создавать `LessonTopic`, не назначать
  произвольную тему и не восстанавливать FK по одному только `direction`**
  (такое действие требует отдельного утверждённого правила, OQ-F5); FK
  остаётся пустым, связь темы фиксируется как отдельный нерешённый
  вопрос/диагностика (шаг 7);
- если структурная подкатегория определена, но правила для `topic_id` нет —
  связь фиксируется как отдельный нерешённый вопрос/диагностика, **данные не
  выдумываются**.

**Важные ограничения:**
- Отсутствие FK `LessonTopic` **не является доказательством**, что материал можно
  автоматически разместить по какому-либо родителю — пустая тема не указывает
  цель размещения.
- Фактический структурный родитель в исходном дереве — HomePage (каталог) —
  **не является достаточным указанием** целевой подкатегории: все материалы
  сейчас дети HomePage, а целевая иерархия требует `LessonPage → SubcategoryPage`.
- **Перед каждым перемещением** проверять актуальное состояние и целевой slug
  (уникальность в целевой подкатегории + полный URL). При конфликте slug при
  переносе — миграция блокируется, конфликт фиксируется в диагностическом
  отчёте.
- Механизм `move()` (атомарность, history revisions, search-индекс) — prototype
  на Wagtail 7.4.3, **неподтверждённая**. Старые URL материалов — redirect по
  разделу 8.3.

**Шаг 4. Переименование slugов категорий (по необходимости).** После переноса
материалов top-level свободен. **Перед снятием временных slug повторно проверить
уникальность всех целевых slug и URL** (по каждому родителю + полные URL).
Любая неразрешённая коллизия — **остановка миграции с диагностикой**.
Автоматические суффиксы (`-2`) и контентные переименования **не вводятся без
решения владельца**. Если все проверки пройдены: slug категории
`python-category` → `python` (URL категории меняется; redirect старый→новый;
категории новые — внешняя привязка/SEO-вес ещё не сформирован).

**Шаг 5. Согласование `direction` и решение о связи темы** (раздел 11):
- `direction`: валидация `direction == ancestor.direction`;
- FK `topic`: **сохраняется/backfill только по утверждённому правилу** (например,
  «направление → тема» — если такое правило **отдельно** утверждено владельцем,
  OQ-F5). Без утверждённого правила FK остаётся как есть (nullable) и связь
  темы фиксируется в диагностике — **не выдумывать** значение темы по
  `direction` (операция B шага 3).

**Шаг 6. Проверка полноты и целостности (инварианты):**
- Каждый `LessonPage` имеет структурный родитель `SubcategoryPage` (в целевой
  иерархии);
- Каждый материал размещен **либо по утверждённому правилу структурного
  размещения (шаг 3a/b), либо в диагностическом отчёте** (и тогда миграция не
  завершена, см. шаг 7);
- Связь темы (`topic_id`): либо сохранена/backfill по утверждённому правилу, либо
  зафиксирована как **отдельный нерешённый вопрос/диагностика**;
- redirect-записи созданы для всех старых URL и проверены (нет циклов/цепочек,
  см. 8.3);
- Блокирующая диагностика (неразмещённые материалы, неполная инвентаризация,
  конфликты slug и другие нарушения обязательных инвариантов) должна быть устранена;
  иначе миграция не завершается. Нерешённая связь `topic_id` при уже однозначном
  утверждённом структурном размещении — отдельная неблокирующая запись отчёта:
  она не отменяет размещение и не требует произвольного заполнения FK. Отчёт
  сохраняется и для таких записей; информационная запись не считается
  блокирующей только потому, что она относится к теме.

**Шаг 7. Завершение (только если все инварианты выполнены).**

**Блокирующие условия завершения:**
- Материал без утверждённого **однозначного** правила структурного
  размещения (включая случай без `topic_id` и без правила темы/направления) —
  миграция **не переходит в финальный статус**, пока владелец не утвердит
  размещение (OQ-F5); такой материал включается в диагностический отчёт
  **до** переноса. **Отсутствие `LessonTopic` FK не трактуется как указание
  родителя, а исходный родитель HomePage — не как указание подкатегории;
  отсутствие `topic_id` само по себе не блокирует при утверждённом правиле
  структурного размещения.** Нельзя одновременно объявлять миграцию завершённой
  и оставлять материалы непосредственными детьми HomePage, если целевая иерархия
  требует `LessonPage → SubcategoryPage`.
- **Связь темы не является блокирующим условием структурной миграции в
  текущих требованиях:** FK `topic` nullable (`null=True, blank=True`, models.py
  L256—262), а целевые инварианты требуют только структурного родителя
  `SubcategoryPage`. Материал с утверждённым правилом структурного размещения,
  но без темы — размещается; FK остаётся пустым, связь темы фиксируется как
  отдельный нерешённый вопрос/диагностика. Если целевые инварианты владельца в
  дальнейшем потребуют обязательной темы (новое требование) — это требует
  отдельного решения владельца (OQ-F5); поведение не выбирается отчётом
  самостоятельно.
- Неполная инвентаризация/сопоставление старых URL, неразрешённые коллизии slug
  (включая повторную проверку шага 4), остаточные конфликты — миграция блокируется
  с диагностикой. **Автоматические суффиксы и контентные переименования без
  решения владельца не вводятся.**

**Техническая реализуемость на Wagtail 7.4.3 (bulk-move, переименование slug,
redirects) — неподтверждённая до прототипа.** Не выполнено в этой среде.

### 10.2 Откат (reverse) — безопасная последовательность, без безусловного удаления

**Правило:** reverse-миграция удаляет только те страницы, которые создала эта
миграция, и только **после** того, как материалы и связи возвращены в прежнее
состояние. Никогда — каскадное удаление без проверок.

**Безопасная обратная последовательность (шаги в порядке выполнения):**

1. **Проверка «не изменилось после миграции» (до любого удаления).**
   `latest_revision_created_at` и количество revisions **недостаточны как
   отдельный критерий** (ревизии могут рождаться автоматически, без ручных
   правок). Достоверный критерий — **снимок исходного состояния**: forward-
   миграция записывает для каждой затронутой страницы/материала baseline
   (например, хэш содержимого + id текущей ревизии + временную метку) в
   таблицу/JSON, хранящиеся миграцией (механизм требует проектирования/
   прототипа — **не существует пока**). При откате каждая затронутая страница
   сравнивается с baseline: любое расхождение (правки, чужой контент,
   пользовательские дети) → **откат останавливается** с диагностикой
   (перечень страниц, baseline и текущего состояния); данные не удаляются.
2. **Вернуть материалы в прежнее состояние — два явно различаемых аспекта:**
   - **Восстановление исходного структурного родителя:** переместить страницу
     материала обратно к исходному родителю в дереве. `LessonTopic` — **сниппет,
     а не структурная страница**, поэтому «вернуть на страницу темы» — неверная
     формулировка: прежним структурным родителем всех материалов **до миграции**
     является HomePage (`LessonPage.parent_page_types =
     ["school.HomePage"]`, models.py L336); после миграции структурный родитель —
     созданная миграцией страница подкатегории.
   - **Восстановление исходного FK/значения `LessonTopic`:** вернуть `topic_id`
     страницы материала к значению, записанному до переноса.
   - **Где и как сохраняются исходные значения до переноса:** forward-миграция
     записывает снимок (прежний родитель, прежний `topic_id`, прежний URL/slug,
     baseline) — механизм сохраняется миграцией (проектирование/прототип;
     не существует пока).
   - Возвращать только те материалы, которые (a) не редактировались (шаг 1) и
     (b) безопасно вернуть — при возврате не возникает конфликта slug или
     конфликта с чужим контентом. Если при возврате возникает конфликт — откат
     останавливается, конфликт фиксируется в отчёте.
3. **Проверка «нет посторонних детей» у созданных миграцией страниц:** после
   шага 2 у созданных миграцией страниц (dashboard-страницы подкатегорий) не
   должно остаться дочерних страниц, которые миграция не создала и не
   переместила. Если есть (например, редактор вручную добавил материал под
   dashboard) — откат останавливается с диагностикой.
4. **Удалить только созданные миграцией и безопасные к удалению страницы:**
   dashboard-страницы (пустые после шага 2), временные страницы, placeholder-
   страницы темы — без дочерних страниц и без редакционных правок. Категории,
   созданные из `DIRECTION_CHOICES` по решению, и страницы тем — **не удаляются**,
   если содержат пользовательский контент; только если созданы миграцией и
   пустые.
5. **Восстановить службы:** вернуть уникальное ограничение, redirect-записи,
   настройки, поиск-индекс.
6. **Отчёт:** фиксируется, что обратное применение завершено, и перечень
   оставленных страниц (если есть) с причиной.

## 12. Получение последних опубликованных материалов по дате и стабильный tie-break

- Текущая сортировка каталога — `order_by("title")` (`models.py:219`), что **не
  соответствует** требованию 1 («от новых к старым»). Предлагается
  `order_by("-first_published_at", "pk")`.
- `first_published_at` — стандартное поле Wagtail `Page`, фиксируется при первой
  публикации (подтверждается publish-логикой в тестах; TECH-DESIGN-001 E.1/F.3).
  Tie-break `pk ASC` — уникальный и стабильный (F.3:
  `first_published_at DESC, material_id ASC`).
- «Последние» трактуется как «публичный каталог отсортирован от новых к старым»
  (все опубликованные). Вариант «только N последних на главной» — вопрос
  владельцу (OQ-F2).

## 13. Формирование полного дерева без N+1

- С деревом страниц (`CategoryPage`, `SubcategoryPage`, `LessonPage`) дерево
  навигации собирается за ≤3 запроса:
  1. `CategoryPage.objects.live().public()` — категории;
  2. `SubcategoryPage.objects.live().public()` (+ `parent_id`/`path`) — подкатегории;
  3. `LessonPage.objects.live().public()` (+ `parent_id`) — материалы.
- Дерево строится в памяти (группировки по родителю); ни один шаблон не делает
  запрос в цикле. На странице категории — тот же набор + список «последних
  материалов категории» (один дополнительный queryset).
- Проверка: `assertNumQueries` на странице категории и странице материала — число
  запросов не растёт с ростом числа подкатегорий/материалов (AC-F-11).

## 14. Доступность раскрываемого дерева, поведение текущего материала, мобильный UX

- **Pattern для нативного `<details>/<summary>` (уточнение по п. 7):** не предлагать
  статическое `aria-expanded`, которое может расходиться с фактическим состоянием.
  Источником truth является атрибут `open` на `<details>` — нативная семантика
  раскрытия; `summary` не требует `aria-expanded`. Если для дерева нужны явные
  ARIA-состояния, они должны вычисляться из фактического состояния (или
  опускаться); `aria-controls`/`id` — только для связи с панелью;
  `aria-label`/`aria-labelledby` — для подписи `summary`.
- **Дерево навигации:** `nav[aria-label]` + disclosure-pattern (`details/summary`);
  текущий материал — `aria-current="page"` (вычисляется из текущего запроса, не
  статический); подкатегория текущего материала — раскрыта (`open`) при рендеринге
  (требование 5); несколько подкатегорий — могут быть раскрыты одновременно
  (`details` это позволяет, требование 6).
- **Клавиатура:** `summary` — Tab + Enter/Space (нативная поддержка); без JS-зависимости
  для базового раскрытия; проверка — HTML-ассертации + ручной чек-лист.
- **Мобильный UX:** адаптивная вёрстка (U-02), дерево сворачивается по умолчанию,
  тап-targets ≥44px (или согласованный размер), horizontal scroll запрещён;
  проверка — ручной чек-лист + HTML-ассертации (AC-F-07).
- **Тесты доступности (предложение):** отсутствие/согласованность
  `aria-expanded` (если применён — тест сравнивает с `open`); наличие
  `aria-current` на текущем материале; наличие `aria-label` на `nav`; keyboard-
  checklist (ручной, фиксируется в отчёте).

### Стратегия тестов

- Автоматические: категории (AC-F-02, AC-F-09), дерево и текущий материал
  (AC-F-03, AC-F-05, AC-F-06), ARIA-ассертации в HTML (AC-F-04, AC-F-07 часть),
  порядок и tie-break (AC-F-01), отсутствие N+1 (AC-F-11), обратимость миграций
  с защитными проверками (AC-F-12), конфликты slug (раздел 9), **разделение
  структурного размещения и связи темы — каждый различимый случай, применимость утверждённых правил, конфликт двух применимых правил, указывающих на разные подкатегории (приоритет правил не выбирается автоматически — только диагностика и остановка), совпадение целевых подкатегорий обоих применимых правил (однозначный результат без предпочтения одного правила другому) и блокирующие условия** (раздел 11,
  матрица 10.2), regression: существующие
  тесты (поиск, noindex, sitemap, slug, похожие, видео, redirects).
- Ручные: ключевая навигация, мобильные устройства, эргономика дерева —
  чек-лист в отчёте, не является автоматической проверкой.
- Ограничение: автоматические тесты проверяют разметку и запросы, но не «удобство»;
  приёмка требует явного решения владельца (OQ-07).

## 16. Открытые вопросы владельцу (только действительно открытые)

Утверждённые решения (иерархия страниц, единый тип материала) **не возвращаются**
сюда (требование п. 6).

1. **OQ-F1 — Точная трактовка шести направлений:** являются ли Scratch, Roblox,
   Python, Unity, ОГЭ, ЕГЭ категориями верхнего уровня (страницы CategoryPage),
   или категории — другая сущность, а направления — тег/фильтр? Без решения не
   создаётся иерархия.
2. **OQ-F2 — Объём списка на главной:** весь каталог, отсортированный от новых к
   старым, или ограниченный список (сколько)?
3. **OQ-F3 — SEO-политика:** индексация страниц категорий/подкатегорий, sitemap,
   canonical, подтверждение `noindex` для query-URL (`?q=`/`?direction=`).
4. **OQ-F4 — Порядок подкатегорий:** по названию, ручной порядок (поле сортировки),
   или другое.
5. **OQ-F5 — Правила заполнения существующих тем:** разбор существующих тем-сниппетов
   в страницы подкатегорий, материалы без темы (разделение структурного
   размещения и связи темы: подкатегория — только по утверждённому правилу; конфликт двух применимых правил (разные подкатегории) —
   диагностика и остановка (преобладание не выбирается автоматически), при применимости обоих правил к одной подкатегории — результат однозначен, используется без предпочтения одного правила другому; отсутствие `topic_id` не блокирует при утверждённом
   правиле структурного размещения; без применимого утверждённого правила —
   блокирует миграцию; FK `topic` при утверждённом правиле структурного
   размещения **не** назначается по `direction` без отдельного утверждённого
   правила), темы, используемые несколькими направлениями (дублирование или
   cross-cutting) — контентное решение.
6. **OQ-F6 — Редирект-политика для старых URL материалов:** принять смену URL + 301
   (вариант U1), или иной механизм (U2/U4) — решение владельца, не принимается
   отчётом (раздел 8).
7. **OQ-F7 — Поле `direction` на материале:** сохранить (de normalized + валидация)
   или удалить (деривация от дерева) — техническое решение, требует проверки при
   реализации.
