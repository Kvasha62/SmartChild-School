## 4. Утверждённые продуктовые требования (Issue #86)

Кратко, без переформулирования смысла:

1. **Главная:** последние опубликованные материалы из всех категорий, от новых к старым.
2. **Категория:** последние опубликованные материалы этой категории + полное дерево её подкатегорий.
3. **Страница материала/урока:** материал + полное дерево соответствующего учебного раздела.
4. Подкатегории — раскрываемые/сворачиваемые блоки; в раскрытом состоянии видны все уроки/материалы подкатегории.
5. На страницах материала дерево навигации показывает текущий материал, выделяет его, автоматически раскрывает содержащую его подкатегорию.
6. Несколько подкатегорий могут быть раскрыты одновременно.
7. Дерево доступно с клавиатуры, имеет корректные ARIA-состояния, удобно на мобильных устройствах.
8. **Вариант А:** статья и урок — единый тип материала.
9. Существующие направления Scratch, Roblox, Python, Unity, ОГЭ, ЕГЭ сохраняются; их точное размещение в новой иерархии — исследуется, не придумывается.
10. Ориентир ИА — общие принципы Metanit.com, без буквального копирования.

## 5. Фактическое состояние frontend на `main` (`5cbc8b3`)

### 5.1 Модель страниц (`school/models.py`)

- `DIRECTION_CHOICES` (L22—28): `scratch`, `roblox`, `python`, `unity`, `oge`, `ege` —
  фиксированный список значений поля `CharField` на `LessonPage`, не страницы.
- `HomePage` (L208—246): `max_count = 1`, `subpage_types = ["school.LessonPage"]`
  (L211—212). `get_context` (L217—246): `LessonPage.objects.child_of(self).live().public().order_by("title")`
  (L219) — **сортировка по названию**, не по дате. Поиск `q` по `title`, `intro`,
  `search_keywords` (L225—231); фильтр `direction` (L222—224, L233—236);
  `catalogue_noindex = "q" in request.GET or "direction" in request.GET` (L243).
- `LessonPage` (L249—356): `direction` (L254), `topic` — FK на сниппет `LessonTopic`
  (L256—262, `on_delete=SET_NULL`, `related_name="lessons"`), `search_keywords` (L263—270),
  `intro`, `video_embed_url` (валидатор Rutube), `body` — `StreamField(LessonBodyBlock)`,
  `tags` — `LessonClusterTaggableManager`. `get_related_lessons` (L301—334): до 3 уроков
  по общей теме, затем по тегам. `parent_page_types = ["school.HomePage"]`,
  `subpage_types = []` (L336—337) — **уроки — прямые дети каталога**, у них нет
  страниц-родителей кроме HomePage.
- `LessonTopic` (L95—149): **сниппет, не страница**; поля `title`, `slug`, `description`;
  нет родительской связи (плоский список); у него нет публичного URL.
- `LessonTag` (L152—175): отдельный пул тегов уроков (taggit).
- Вариант А (статья = урок) **уже согласован с текущей моделью**: существует единый
  тип `LessonPage`, отдельного типа «статья» нет.

### 5.2 URL и служба страниц

- `HomePage(slug="smartchild-school")` создаётся в миграции `0001_initial.py` (L16—40)
  как дочерняя страница корня Wagtail, и `Site.root_page` переключается на неё.
  Следовательно: корневой URL `/` обслуживает HomePage (site root); публичный URL
  урока — site-relative путь урока, например `/{slug-урока}/` (полный `url_path`
  содержит префикс: `/smartchild-school/{slug}/`).
- Маршруты: `/sitemap.xml` (wagtail sitemaps), Wagtail-URLs; `/cms/` — редактор.

### 5.3 Шаблоны, статические ресурсы, доступность

- `base.html`: `lang="ru"`, внешние CSS/JS, header/footer.
- `home_page.html`: навигация направлений (L15—19), форма поиска (L22—37), список

## 6. Варианты архитектуры и аргументированный выбор

### Вариант A — рекомендуемый: «страницы категорий + сниппеты подкатегорий +
материалы остаются детьми каталога»

- Новый тип страниц `CategoryPage` (детский тип `HomePage`, `subpage_types`
  добавляет `"school.CategoryPage"`). Поля: `direction` (choices = `DIRECTION_CHOICES`),
  SEO-поля. URL: `/{slug-категории}/` (соседние с уроками, collision-free при разных
  slug).
- Подкатегории остаются сниппетами `LessonTopic` с двумя новыми полями:
  `parent` (FK на `LessonTopic`, `null=True`) — для вложенности подкатегорий, и
  `direction` (choices) — чтобы подкатегории принадлежали категории. Миграция данных
  создаёт 6 страниц категорий из `DIRECTION_CHOICES` (если владелец подтвердит,
  что направления = категории — вопрос OQ-F1); существующие уроки **не трогаются**.
- Материалы (`LessonPage`) остаются детьми `HomePage` → **URL уроков не меняются**
  (`/{slug-урока}/`), состояние публикации, поиск, фильтрация и редакторский процесс
  сохраняются.
- Логическая вложенность «категория → подкатегория → материал» достигается через
  поля: `LessonPage.direction` + `LessonPage.topic` (как сейчас) и новые
  `LessonTopic.parent`/`LessonTopic.direction`; физически дерево страниц остаётся
  shallow (`HomePage → CategoryPage`), подкатегории — сниппеты.
- Дерево навигации рисуется общим include (например,
  `school/includes/learning_tree.html`) из prefetch-данных: один запрос на категории,
  один на темы (с `parent`), один на опубликованные уроки → дерево в памяти, без N+1.

### Вариант B — полная page-tree: материалы физически под категориями/подкатегориями

- Создать `CategoryPage` и `SubcategoryPage`; переместить уроки под страницы
  подкатегорий. Преимущества: «естественная» вложенность страниц, Wagtail-навигация,
  возможны URL подкатегорий. Недостатки: **меняются URL всех уроков**
  (`/{slug}/` → `/{category}/{subcategory}/{slug}/`), требуется миграция перемещения
  + redirects для старых URL, изменения в `parent_page_types`/`subpage_types`, ручная
  перепроверка публикаций/sitemap/поиска; риск для «сохранения текущих URL» и SEO.
  Не соответствует предпочтению сохранить URL без redirect-цепочек (TECH-DESIGN-001 §H
  предписывает 301 только при согласованной политике).

### Вариант C — виртуальные категории (Django-views без страниц Wagtail)

- URL категории обслужить собственным видом. Недостатки: страницы категорий не
  попадут автоматически в sitemap/навигацию/историю Wagtail, нужно дублировать
  редакторский процесс, проверку прав; SEO-логика выносится вручную. Не рекомендуется,
  пока редакторский процесс остаётся в Wagtail.

### Вариант D — без новых страниц: только дерево в шаблонах

- Наить дерево навигации из существующих данных (topic + lessons) и «категорию»
  реализовать как `?direction=`-фильтр на главной. Недостатки: требования 2/3
  требуют страницы категории со «полным деревом подкатегорий» и деревом на странице
  материала; фильтр-URL не даёт pages-контекста (SEO, canonical, sitemap). Не
  закрывает требования.

### Выбор

**Вариант A.** Он сохраняет все текущие URL и публикации, минимизирует миграционный
риск, использует готовые Wagtail-механики (страницы + сниппеты), соответствует
варианту А (единый тип материала) и производному принципу «материал — метаданные
о категории/подкатегории, не children-узлы». Подкатегории как сниппеты оправданы,
пока требования не требуют URL подкатегорий (они требуют блоки и дерево навигации,
не адреса подкатегорий). Переход к страницам подкатегорий (Вариант B) остаётся
поздней эволюцией при решении владельца о URL подкатегорий.

## 7. Рекомендуемая модель Wagtail-страниц и допустимая вложенность

## 8. Сохранение текущих URL, публикаций, поиска, фильтрации, SEO и редакторского процесса

- **URL уроков не меняются** (Вариант A): `/{slug}/` остаётся 200; тесты
  `test_published_lesson_appears_in_catalogue_and_opens_publicly`, redirect-тесты и
  sitemap-тесты остаются зелёными. Redirect-цепочек не вводится.
- **Публикации:** `live/public` и revisions не трогаются; новый тип страниц категорий
  создаётся публичным (live) при миграции; каталог и поиск по-прежнему filter
  `.live().public()`.
- **Поиск и фильтр:** контракт OQ-02/OQ-04 сохраняется: `q` по title/intro/
  search_keywords, `direction` как фильтр, пустой запрос — без поиска, query-URL —
  `noindex` (L243). Категория-страница использует тот же queryset-паттерн
  (`.live().public().filter(direction=…)`), не заводит второй поиск.
- **SEO:** sitemap (wagtail) получит страницы категорий; meta description для
  категорий — editor-поля с fallback; canonical/policy — решение владельца (OQ-F6).
- **Редакторский процесс:** редакторский интерфейс не ломается: уроки редактируются как
  раньше; категории создаются как страницы через CMS; сниппеты тем дополняются
  полями parent/direction в тех же panel.

## 9. План безопасного перехода и обратимость миграций

1. **Миграция схемы (forward):** `AddField LessonTopic.parent`, `AddField
   LessonTopic.direction`, `CreateModel CategoryPage`. `makemigrations --check` в CI
   остаётся чистым.
2. **Миграция данных:** создаёт 6 `CategoryPage` (slug из `DIRECTION_CHOICES`:
   `scratch`, `roblox`, `python`, `unity`, `oge`, `ege`), если их ещё нет; не трогает
   уроки. `RunPython` с `reverse` — удалить созданные страницы категорий (как
   `delete_homepage` в `0001_initial.py`).
3. **Обратимость:** миграции data-forward должны иметь data-reverse; разбор
   существующих тем на parent/direction — content-решение владельца (OQ-F2/OQ-F3),
   миграция только добавляет поля, не перераспределяет темы без решения.
4. **Rollback-покрытие:** тесты `LessonBodyMigrationTests` (вперед/назад) — шаблон для
   новых миграций; проверка `migrate` в CI и `migrate --check`.
5. **Минимальный первый шаг:** Вариант A без изменения URL уроков и без перемещения
   данных материалов — наименее рискованный вклад, который уже даёт страницы
   категорий, дерево навигации и раскрываемые подкатегории.

## 10. Получение последних опубликованных материалов по дате и стабильный tie-break

- Текущая сортировка каталога — `order_by("title")` (`models.py:219`), что **не
  соответствует** требованию 1 («от новых к старым»). Предлагается
  `order_by("-first_published_at", "pk")`.
- `first_published_at` — стандартное поле Wagtail `Page`, фиксируется при первой
  публикации и не меняется при перепубликации (соответствует E.1/F.3
  TECH-DESIGN-001). Tie-break `pk ASC` — уникальный и стабильный (F.3:
  `first_published_at DESC, material_id ASC`).
- «Последние» трактуется как «публичный каталог отсортирован от новых к старым»
  (все опубликованные). Вариант «только N последних на главной» — вопрос владельцу
  (OQ-F5), так как текущий каталог показывает весь список.
- В search-выдаче tie-break аналогично: `rank DESC, pk ASC` (F.3); текущий домашний
  поиск — `icontains` без rank, оставлен как есть (MVP-контракт OQ-02).

## 11. Формирование полного дерева без N+1

- Единый include `learning_tree.html` принимает данные, собранные за ≤3 запроса:
  1. `CategoryPage.objects.live().public().filter(direction=…)` — категории;
  2. `LessonTopic.objects.all()` (+ `parent_id`) — все подкатегории;
  3. `LessonPage.objects.live().public().filter(direction=…)` — все опубликованные
     уроки (+ `topic_id`).
- Дерево строится в памяти: группы уроков по `topic_id`, подкатегории связываются по
  `parent_id`. Ни один шаблон не делает запрос в цикле.
- Проверка: `assertNumQueries` на странице категории и странице материала — число
  запросов не растёт с ростом числа подкатегорий/уроков (AC-F-11).

## 12. Доступность раскрываемого дерева, поведение текущего материала, мобильный UX

- Раскрытие: нативный `<details>/<summary>` (как `blocks/accordion.html`) — keyboard
  accessible без JS; `aria-expanded` на `summary`, `aria-controls`/`id` связь;
  несколько раскрытий одновременно (требование 6) — `<details>` это позволяет.
- Дерево навигации: `nav[aria-label]` + семантика: `role="tree"`/`treeitem` либо
  disclosure-pattern (рекомендуется disclosure, соответствующий «раскрываемые
  блоки»); текущий материал — `aria-current="page"`; родительская подкатегория —
  раскрыта (`open`/`aria-expanded="true"`) автоматически (требование 5).
- Поведение текущего материала: выделение + авто-раскрытие без JS-зависимости
  (рендеринг в шаблоне: для текущего урока ставится `open` на его подкатегории).
- Мобильный UX: адаптивная вёрстка (U-02), дерево сворачивается по умолчанию, тап-targets
  ≥44px (или согласованный размер), horizontal scroll запрещён; проверка — ручной
  чек-лист + HTML-ассертации (AC-F-07).
