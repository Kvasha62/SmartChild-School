# Production-развёртывание SmartChild-School: runbook

## Статус документа

Этот runbook описывает **подготовку** к production-развёртыванию, а не
выполненное развёртывание. По состоянию на подготовку документа:

- сайт нигде публично не развёрнут;
- хостинг, регион, домен и DNS не выбраны;
- поставщик SMTP не выбран, реальная почта не подключена;
- постоянное хранение медиафайлов на конкретной платформе не настроено;
- резервное копирование production-данных не выполняется, потому что
  production-данных ещё нет;
- мониторинг и внешний сбор ошибок не подключены.

Поэтому проект **нельзя** считать полностью готовым к публичному запуску.
Готова переносимая и проверяемая конфигурация приложения: отдельный модуль
`config/production_settings.py`, Docker-образ с Gunicorn и WhiteNoise,
проверки CI и процедуры ниже. Остающиеся блокирующие решения владельца
перечислены в конце документа; без них публичный запуск невозможен.

Связанные документы: [локальный запуск TECH-001](TECH-001-local-development.md),
[TECH-DESIGN-001](TECH-DESIGN-001.md) (в частности разделы G и L),
[границы продукта](../product-scope.md).

## Целевая схема (без выбора провайдера)

```
Интернет ──HTTPS──> TLS-терминация (reverse proxy / балансировщик платформы)
                         │  HTTP внутри доверенной сети,
                         │  заголовок X-Forwarded-Proto перезаписывается прокси
                         ▼
                    Gunicorn (контейнер, не root) ──> PostgreSQL 18.6
                         │
                         ├── статические файлы: WhiteNoise из образа
                         └── медиафайлы: DJANGO_MEDIA_ROOT на постоянном хранилище
                    SMTP ──> внешний почтовый сервис (выбирает владелец)
```

Выборы, зафиксированные этой подготовкой, и их обоснование:

- **WSGI-сервер — Gunicorn.** Стандартный production-сервер для Django;
  `runserver` в production не используется.
- **Статические файлы — WhiteNoise** с
  `CompressedManifestStaticFilesStorage`. Для текущего объёма (один сайт
  Wagtail, статика собирается в образ) отдельный CDN или объектное
  хранилище не нужны; это сохраняет переносимость между платформами.
  Если владелец позже выберет CDN/объектное хранилище, точка замены —
  `STORAGES` в `production_settings.py`.
- **Медиафайлы не отдаются WhiteNoise.** Загрузки Wagtail (изображения,
  документы) лежат в `DJANGO_MEDIA_ROOT`; как их раздаёт выбранная
  платформа (веб-сервер, файловый сервис платформы, объектное хранилище) —
  блокирующее решение при выборе хостинга.
- **Миграции БД — отдельный ручной этап выпуска**, а не часть старта
  приложения: старт нескольких копий не должен гонять миграции параллельно.
- **Секреты только из переменных окружения.** В репозитории нет реальных
  секретов; значения из `.env.production.example` — шаблоны, которые
  production-конфигурация отклоняет или которые заведомо неработоспособны.

## Переменные окружения

Production запускается с `DJANGO_SETTINGS_MODULE=config.production_settings`
(в Docker-образе уже установлено). Отсутствие обязательной переменной,
слабый секретный ключ, `DEBUG=true` или подстановочный `*` в хостах приводят
к немедленной ошибке `ImproperlyConfigured` при старте; текст ошибки
называет переменную, но никогда не печатает значения секретов.

### Обязательные

| Переменная | Назначение | Требования |
| --- | --- | --- |
| `DJANGO_SECRET_KEY` | Секретный ключ Django | Случайный, ≥ 50 символов, уникальный для окружения. Генерация: `python -c "import secrets; print(secrets.token_urlsafe(64))"`. Демонстрационные значения из репозитория отклоняются |
| `DJANGO_ALLOWED_HOSTS` | Точные имена хостов через запятую | Без `*`, например `school.example.org` |
| `WAGTAILADMIN_BASE_URL` | Публичный origin для ссылок в письмах Wagtail (уведомления, сброс пароля) | `https://…` без credentials/query, например `https://school.example.org` |
| `DJANGO_MEDIA_ROOT` | Каталог загрузок Wagtail | **Абсолютный путь на постоянном хранилище**, смонтированном в окружение приложения |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST` | Доступ к PostgreSQL | Пустой пароль не принимается; пароль хранится только в секретах платформы |
| `DJANGO_EMAIL_HOST` | SMTP-сервер выбранного провайдера | — |
| `DJANGO_DEFAULT_FROM_EMAIL` | Адрес отправителя | На домене владельца после настройки SPF/DKIM/DMARC у провайдера |

### Необязательные (в скобках — значение по умолчанию)

| Переменная | Назначение |
| --- | --- |
| `DB_PORT` (`5432`), `DB_CONN_MAX_AGE` (`60`), `DB_SSLMODE` (не задан) | PostgreSQL; `DB_SSLMODE=require` — если управляемая БД требует TLS |
| `DJANGO_EMAIL_PORT` (`587`), `DJANGO_EMAIL_USE_TLS` (`true`), `DJANGO_EMAIL_USE_SSL` (`false`) | SMTP; TLS и SSL одновременно запрещены: 587+STARTTLS или 465+SSL |
| `DJANGO_EMAIL_HOST_USER`, `DJANGO_EMAIL_HOST_PASSWORD` | Учётные данные SMTP; задаются только парой. Оба пустые допустимы только для внутреннего relay без аутентификации |
| `DJANGO_EMAIL_TIMEOUT` (`10`), `DJANGO_SERVER_EMAIL` (= `DJANGO_DEFAULT_FROM_EMAIL`) | Таймаут SMTP и отправитель служебных писем Django |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | По умолчанию выводится из `WAGTAILADMIN_BASE_URL`. Явно задавайте при нескольких https-origin; записи только `https://…` |
| `DJANGO_STATIC_ROOT` (`/app/staticfiles` в образе) | Куда собирается статика; обычно не менять |
| `DJANGO_SECURE_SSL_REDIRECT` (`true`) | Редирект http→https. Выключать только если редирект гарантированно делает прокси и приложение недостижимо в обход него. Пути `/health/live/` и `/health/ready/` исключены из редиректа для проб платформы — они отдают только статусное слово |
| `DJANGO_SECURE_HSTS_SECONDS` (`3600`) | Начинайте с малого значения; повышайте (например до `31536000`) после проверки HTTPS и финальной доменной схемы |
| `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS` (`false`), `DJANGO_SECURE_HSTS_PRELOAD` (`false`) | Включать только отдельным решением, когда **все** поддомены гарантированно на HTTPS; preload — практически необратимое обязательство |
| `DJANGO_TRUST_PROXY_HEADERS` (`false`) | `true` только за доверенным прокси, который всегда перезаписывает `X-Forwarded-Proto`, и если порт приложения недоступен извне напрямую. Иначе заголовок можно подделать |
| `DJANGO_LOG_LEVEL` (`INFO`) | Уровень логов в stderr; сбор и хранение — на платформе |
| `WEB_CONCURRENCY` | Число воркеров Gunicorn под ресурсы платформы |

Локальная разработка использует другой модуль (`config.settings`) и
другой контракт: почта по умолчанию — консольный backend (письма печатаются
в терминал, SMTP не нужен), загрузки — в `./media`. Не переносите локальные
значения и placeholder-секреты в production.

## Сборка и запуск

### Сборка образа

```bash
docker build -t smartchild:<тег-релиза> .
```

При сборке выполняется `collectstatic` на синтетических build-only
значениях: они нужны только для импорта production-настроек, не являются
учётными данными и не попадают в окружение запущенного контейнера.
Приложение в образе работает от пользователя `app` (uid 10001), не от root.

### Порядок выпуска (каждый шаг — отдельно, в этом порядке)

1. Зафиксируйте полный SHA выпускаемого коммита и тег образа.
2. Соберите (или получите из реестра) образ именно этого SHA.
3. Настройте секреты и переменные окружения на платформе; проверьте, что
   `DJANGO_MEDIA_ROOT` указывает на постоянное хранилище и что том
   смонтирован и доступен на запись пользователю приложения.
4. Сделайте резервную копию БД и медиа (см. ниже) — до миграций.
5. **Отдельной одноразовой командой** примените миграции:

   ```bash
   docker run --rm --env-file <production-env> \
        -v <постоянный-том>:/srv/media \
     smartchild:<тег-релиза> python manage.py migrate --noinput
   docker run --rm --env-file <production-env> \
     -v <постоянный-том>:/srv/media \
     smartchild:<тег-релиза> python manage.py migrate --check
   ```

   Статика уже собрана в образ; повторный `collectstatic` при обычном
   выпуске не нужен. При запуске без Docker выполните эквивалентно:
   `python manage.py collectstatic --noinput` с production-настройками до
   старта WSGI-сервера.
6. Запустите/обновите сервис приложения (команда образа по умолчанию —
   WSGI-сервер на порту 8000). Миграции при старте не выполняются.
7. Выполните проверки после выпуска (см. ниже). При провале — откат.

Пример локального запуска образа для проверки (не production-топология;
PostgreSQL и том должны существовать, значения — синтетические):

```bash
docker run --rm -p 127.0.0.1:8000:8000 --env-file .env.production.local \
  -v smartchild-media:/srv/media smartchild:<тег-релиза>
```

### Создание администратора Wagtail

Публичной регистрации редакторов нет. Первую учётную запись создаёт
уполномоченный администратор интерактивно (пароль не передаётся аргументами
командной строки и не пишется в логи):

```bash
docker run --rm -it --env-file <production-env> \
  -v <постоянный-том>:/srv/media \
  smartchild:<тег-релиза> python manage.py createsuperuser
```

Вход в CMS: `https://<домен>/cms/`. Политика MFA, сроков сессий и количества
редакторских записей — открытое решение владельца (G-ACCESS в
TECH-DESIGN-001); до его принятия используйте индивидуальные записи,
уникальные пароли из менеджера паролей и не делитесь одной записью на
нескольких людей.

## HTTPS и reverse proxy

Обязательные требования к выбранной платформе:

- Публичный доступ — только HTTPS с валидным сертификатом для финального
  домена; HTTP либо редиректится прокси, либо приложением
  (`SECURE_SSL_REDIRECT`, по умолчанию включён).
- Если TLS терминируется на прокси/балансировщике: прокси обязан
  перезаписывать `X-Forwarded-Proto`, порт 8000 приложения не должен быть
  доступен из интернета в обход прокси, и только тогда устанавливается
  `DJANGO_TRUST_PROXY_HEADERS=true`.
- Прокси должен сохранять исходный `Host`, входящий в `DJANGO_ALLOWED_HOSTS`;
  запросы с чужим `Host` приложение отклоняет (HTTP 400) — это ожидаемо,
  включая пробы: контейнерный `HEALTHCHECK` уже подставляет первый
  разрешённый хост.
- Лимиты размера тела запроса на прокси не должны быть ниже лимита загрузки
  изображений Wagtail (10 МБ в текущих настройках).
- HSTS наращивается постепенно: сначала значение по умолчанию (3600 с),
  после подтверждения, что весь сайт стабильно работает по HTTPS, —
  повышение; subdomains и preload — только отдельным решением владельца.
- Cookie сессии и CSRF в production всегда `Secure`, поэтому админка по
  чистому HTTP работать не будет — это намеренно.

## Почта (SMTP) и уведомления Wagtail

Локально почта печатается в консоль и SMTP не требуется (см. TECH-001);
ошибка `ConnectionRefusedError` при уведомлениях Wagtail в локальной среде
этой конфигурацией устранена. В production всегда используется SMTP
(`django.core.mail.backends.smtp.EmailBackend`); провайдера выбирает
владелец. Типичные варианты порта: `587` + `DJANGO_EMAIL_USE_TLS=true` или
`465` + `DJANGO_EMAIL_USE_SSL=true` (одновременно включать оба флага
конфигурация запрещает).

После выбора провайдера и до публичного запуска владелец/администратор:

1. Создаёт у провайдера отдельную учётную запись/ключ именно для этого сайта.
2. Настраивает для домена SPF, DKIM и DMARC по инструкции провайдера,
   иначе письма будут попадать в спам или отклоняться.
3. Вносит `DJANGO_EMAIL_*` в секреты платформы (не в Git) и перезапускает
   приложение.
4. Проверяет отправку на **свой тестовый адрес** (не на адреса детей и не
   на реальные адреса третьих лиц):

   ```bash
   docker run --rm --env-file <production-env> \
     smartchild:<тег-релиза> python manage.py shell -c \
     "from django.core.mail import send_mail; print(send_mail('SmartChild SMTP check', 'Synthetic test message.', None, ['<ваш-тестовый-адрес>']))"
   ```

   Ожидается `1` и письмо во входящих. Затем в Wagtail: отправить страницу
   на модерацию/опубликовать тестовую страницу и проверить уведомление;
   запросить сброс пароля редактора и проверить ссылку (она строится от
   `WAGTAILADMIN_BASE_URL`).
5. При ошибках смотреть логи приложения: конфигурация не логирует пароль
   SMTP; не вставляйте секреты в обращения в поддержку и в Issue.

Автоматические тесты в CI реальные письма не отправляют: тестовый runner
Django подменяет backend на in-memory.

## Постоянное хранение медиафайлов

- `DJANGO_MEDIA_ROOT` обязан указывать на постоянное хранилище платформы
  (примонтированный том/диск). Каталог `/srv/media` в образе — только точка
  монтирования: **без тома загрузки живут в эфемерной файловой системе
  контейнера и пропадут при его замене**. Production-конфигурация требует
  явный абсолютный путь именно чтобы это не произошло молча.
- Пользователь приложения (uid 10001) должен иметь право записи в этот
  каталог; производные изображения Wagtail создаются там же.
- Раздача `/media/` в production приложением не выполняется (в отличие от
  локального `DEBUG`-режима). Платформа/веб-сервер должна отдавать файлы из
  `DJANGO_MEDIA_ROOT` по `/media/`, либо потребуется отдельное решение по
  объектному хранилищу. Учитывайте приватность: файлы из неопубликованных
  материалов не должны становиться публично доступными только из-за того,
  что файл существует, — политика доступа к медиа сверяется с требованиями
  TECH-DESIGN-001 (раздел G.3) при выборе способа раздачи.
- Несколько копий приложения одновременно требуют общего хранилища
  (сетевой том или объектное хранилище); локальный том одного контейнера
  для горизонтального масштабирования не подходит.

## Резервное копирование и восстановление

Политика копирования (частота, срок хранения, RPO/RTO, хранение вне
площадки, ответственный) — **не принята**; раздел фиксирует только
переносимую процедуру, которую владелец наполнит параметрами при выборе
платформы. Копировать нужно парой «БД + медиа» с одной меткой времени:
дамп БД без медиа (и наоборот) не восстанавливает сайт целиком.

Создание копии (примеры с доступом к PostgreSQL и тому; секреты не пишите
в командную строку открыто — используйте окружение/`.pgpass` платформы):

```bash
# PostgreSQL (custom format, сжимаемый, восстанавливается pg_restore)
pg_dump --format=custom --no-owner \
  --host=<db-host> --username=<db-user> --dbname=<db-name> \
  --file=smartchild-db-<YYYYMMDD-HHMM>.dump

# Медиафайлы из DJANGO_MEDIA_ROOT
tar --create --gzip --file=smartchild-media-<YYYYMMDD-HHMM>.tar.gz \
  --directory=<DJANGO_MEDIA_ROOT> .
```

Восстановление (выполняется в пустую БД и пустой каталог медиа на
тестовом окружении при drills; на production — только в окно обслуживания):

```bash
pg_restore --clean --if-exists --no-owner \
  --host=<db-host> --username=<db-user> --dbname=<db-name> \
  smartchild-db-<YYYYMMDD-HHMM>.dump

tar --extract --gzip --file=smartchild-media-<YYYYMMDD-HHMM>.tar.gz \
  --directory=<DJANGO_MEDIA_ROOT>
# Проверьте владельца файлов: каталог должен быть доступен uid 10001.

docker run --rm --env-file <production-env> -v <том>:/srv/media \
  smartchild:<тег-релиза> python manage.py migrate --check
```

Требования к процедуре независимо от платформы: копии хранятся вне узла
приложения, доступ к ним ограничен (в них содержимое сайта и служебные
данные редакторов), восстановление регулярно проверяется на отдельном
окружении с замером фактического времени, а не только фактом «задача
копирования завершилась». Копии с реальными данными нельзя выгружать в
публичные места, Issue или PR.

## Проверки после выпуска

Минимум для каждого выпуска, фиксируется вместе с SHA образа:

```bash
curl -fsS https://<домен>/health/live/    # {"status": "ok"} — процесс жив
curl -fsS https://<домен>/health/ready/   # {"status": "ok"} — PostgreSQL отвечает
curl -fsSI https://<домен>/ | head        # 200, HSTS по мере наращивания
curl -fsSI http://<домен>/ | head         # 301 на https (или редирект прокси)
```

Плюс вручную: главная страница и каталог открываются без входа; страница
опубликованного синтетического/служебного урока открывается, черновик не
виден анонимно; статика админки загружается (нет «голого» HTML на
`/cms/login/`); вход редактора работает; загрузка тестового изображения в
черновик проходит и файл появляется в `DJANGO_MEDIA_ROOT`, а после рестарта
контейнера не пропадает; тестовое письмо/уведомление доходит (см. раздел
почты); в логах нет повторяющихся ошибок 500.

Ожидаемые предупреждения `check --deploy`: конфигурация намеренно даёт три
warnings и ни одной ошибки — `security.W005` и `security.W021` (HSTS
subdomains/preload выключены до утверждения доменной схемы) и
`security.W019` (`X_FRAME_OPTIONS=SAMEORIGIN` вместо `DENY`, потому что
предпросмотр страниц Wagtail работает в same-origin iframe; встраивание
чужими сайтами при этом по-прежнему запрещено). Появление любого другого
предупреждения или ошибки — повод остановить выпуск и разобраться, а не
отключать проверку. Защитные настройки ради «зелёных» проверок не ослабляются.

## Откат

1. Приложение: верните сервис на предыдущий тег образа (тот же набор
   переменных окружения). Это основной и быстрый путь отката.
2. Миграции: откат образа допустим без отката схемы только если миграции
   выпуска обратносовместимы (добавление таблиц/колонок). Если выпуск
   содержал разрушающие миграции, сначала оцените их обратимость
   (`python manage.py migrate <app> <предыдущая-миграция>`) на копии БД;
   при сомнении — восстановление пары «БД + медиа» из копии, сделанной
   перед выпуском, с потерей изменений после неё (это цена, которую задаёт
   ещё не принятый RPO).
3. После отката повторите проверки после выпуска и зафиксируйте в отчёте:
   SHA проблемного и рабочего образов, причину, затронутые миграции.

## Блокирующие решения владельца (без них публичного запуска нет)

| # | Решение | Варианты и последствия |
| --- | --- | --- |
| 1 | Хостинг и регион, бюджет | PaaS (меньше эксплуатации, привязка к провайдеру) vs VPS + Docker (дешевле/переносимее, обновляет ОС владелец) vs managed-контейнеры. Регион влияет на задержки для аудитории и юрисдикцию данных |
| 2 | Домен, DNS, выпуск TLS-сертификатов | Свой домен обязателен для HSTS/почты; автообновление сертификатов (например ACME) vs ручное — ручное рискует простоем по истечении |
| 3 | Где терминируется TLS и как раздаётся `/media/` | Прокси платформы / отдельный веб-сервер / объектное хранилище. Определяет `DJANGO_TRUST_PROXY_HEADERS`, приватность медиа черновиков и стоимость трафика |
| 4 | Постоянное хранилище медиа при росте | Один том (просто, одна копия приложения) vs объектное S3-совместимое хранилище (масштаб и независимость от узла, но провайдер, ключи, политика доступа, цена) |
| 5 | SMTP-провайдер и доменная репутация | Транзакционный сервис vs SMTP хостинга; в обоих случаях нужны SPF/DKIM/DMARC и отдельный ключ для сайта; без рабочей почты нет уведомлений модерации и сброса пароля |
| 6 | Политика резервного копирования: RPO/RTO, частота, retention, off-site хранение, ответственный | Редкие копии дешевле, но потеря контента между копиями больше; без проверенных drills восстановления RPO/RTO — декларация, а не факт |
| 7 | Мониторинг, сбор ошибок, хранение логов и алерты | Внешний сервис ошибок (удобно, передача данных третьей стороне, возможная плата) vs только логи платформы и ручные проверки; нужны правила, что нельзя писать в логи |
| 8 | Редакторский доступ (G-ACCESS) | Число записей, MFA, сроки сессий, порядок выдачи/отзыва; влияет на риск компрометации CMS сильнее, чем любой заголовок |
| 9 | Staging-окружение и реестр образов | Отдельный staging с синтетическими данными (безопаснее выпуски, двойная стоимость/поддержка) vs только CI + production; где хранятся и как долго живут теги образов для отката |
| 10 | Продуктовые блокеры запуска вне этого runbook | Утверждённые перечни стартовых материалов, способ работы с Rutube, поиск — по Issue #4 и `docs/product-scope.md`; техническая готовность не заменяет их |

## Что проверяет CI

`.github/workflows/ci.yml` на каждом PR: установка закреплённого
`requirements.txt` и `pip check` на Python 3.13.17; `manage.py check`;
`makemigrations --check --dry-run`; миграции на PostgreSQL 18.6;
`manage.py test` (включая контрактные тесты production-конфигурации);
`migrate --check`; `check --deploy` и `collectstatic` с production
настройками на синтетических значениях; отдельная job собирает Docker-образ,
проверяет запуск не от root и smoke-сценарий «миграции отдельной командой →
приложение за эмулированным TLS-прокси → `/health/live|ready/`, главная
страница, статический файл». CI не отправляет реальные письма и не
использует production-секреты. Успешный CI не является ни деплоем, ни
разрешением на него.
