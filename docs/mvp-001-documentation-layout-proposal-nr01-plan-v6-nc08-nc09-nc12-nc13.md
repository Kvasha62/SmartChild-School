## 1. NC-08 — определение «этап» для правила ПТ-1

**Проблема:** ПТ-1 устанавливает таблицу этапов как растущую хронику, но не определяет, что считается этапом.

**Уточнённый текст ПТ-1 (заменяет пункты правила ПТ-1 в §4.5 плана версии 5):**

1. **Этап** — одна логически самостоятельная и проверяемая единица изменения, отражённая отдельной строкой таблицы этапов §8 основного документа. Строка должна позволять установить содержание изменения и связанный PR или иной проверяемый результат.
2. Один PR может реализовать несколько этапов, если в нём выполнены несколько самостоятельных единиц изменения; номер PR не является определением этапа.
3. Каждый завершённый этап фиксируется отдельной строкой хроники. Если номер PR, итоговый SHA или иной результат ещё неизвестен, строка добавляется последующим изменением после появления проверяемых сведений.
4. Таблица является растущей хроникой, а не исчерпывающим списком коммитов. Отставание таблицы от последнего изменения допустимо до внесения следующей строки и само по себе не считается дефектом при наличии этого примечания.
5. Этап считается завершённым для целей хроники после слияния соответствующего изменения и проверки итогового состояния по полному SHA. До слияния допускается фиксировать этап как выполняемый, но его нельзя описывать как завершённый.

**Критерий устранения NC-08:** понятие «этап» определено через самостоятельную проверяемую единицу, связь строки с результатом и правило завершения; PR и этап явно не отождествляются.

**Уточнённый фрагмент проекта записи (§3.2):**

> Отдельного решения владельца по полному SHA в GitHub на момент подготовки проекта записи в версии 5 не было: ревью в PR #19—#29 — 0; комментарии в этих PR — только от `sourcery-ai[bot]`. Этот диапазон отражает исторический срез при подготовке версии 5 (2026-10-21), а не текущее состояние PR и не вывод о PR, созданных позднее.

**Согласование остальных упоминаний:**

- В описании контрольного состояния версии 5 диапазон PR #19—#29 допустим только с явной пометкой, что это срез на момент подготовки версии 5.
- В проекте записи L-02 и в пояснениях к проверке используется тот же диапазон и тот же исторический смысл; диапазон #19—#25 не оставляется как будто исчерпывающий.
- Позднейшие изменения состояния PR (включая закрытие без слияния PR #19—#22 и слияние PR #37—#38) фиксируются в актуальных отчётах, а не переписывают исторический срез версии 5.

**Критерий устранения NC-09:** ни одно упоминание #19—#25 не представлено как полный диапазон проверенных PR версии 5; исторический диапазон унифицирован как #19—#29 и снабжён датой/оговоркой о срезе.

## 3. NC-12 — критерии готовности реализующего PR

**Проблема:** план не содержит сводного критерия, по которому можно решить, готов ли PR с реализацией NR-01 к рассмотрению и проверке.

Перед запросом ревью реализующий PR должен пройти следующий чек-лист.

### 3.1. Область и состояние

- [ ] В PR указан базовый SHA `main` и полный HEAD SHA; список изменённых файлов соответствует разрешённому объёму.
- [ ] Реализуются только правки NR-01, разрешённые владельцем; основной документ — единственный изменяемый файл реализации, если отдельное разрешение не определяет иначе.
- [ ] Указано состояние L-02 (A, B или C) на момент применения правки строки 6; выбранная формулировка строки 6 соответствует матрице §4.3.1.
- [ ] Изменение строки L-02 в §7 не применяется без отдельного разрешения владельца, указанного в плане.

### 3.2. Содержательные инварианты

- [ ] Все обязательные правки плана отражены; каждая опциональная правка либо реализована по согласованному правилу, либо явно отмечена как неприменённая с основанием.
- [ ] Дата в строке 4 соответствует дате применения правки по ПТ-3, если ПТ-3 утверждён владельцем; номер редакции соответствует ПТ-2.
- [ ] Определения Markdown-ссылок в документе в точности совпадают с множеством используемых ссылок; все относительные ссылки разрешимы.
- [ ] Таблица этапов соответствует ПТ-1; формулировки не утверждают фактов о решении владельца или статусе записи сверх фактически подтверждённых данных.
- [ ] Не изменены файлы, ветви, PR и замечания вне разрешённой области; отсутствуют секреты и реальные персональные данные.

### 3.3. Проверки и отчётность

- [ ] Выполнены доступные проверки форматирования и ссылок, включая `git diff --check`; результат каждой проверки записан, непроведённые проверки перечислены явно.
- [ ] Отчёт PR содержит изменённые файлы, краткое описание, базовый и итоговый SHA, выполненные/не выполненные проверки и известные ограничения.
- [ ] После слияния проведена пост-слияниeвая проверка по `CONTRIBUTING.md`, п. 8: подтверждены итоговый SHA, соответствие `main`, ссылки и отсутствие непредусмотренных изменений.
- [ ] PR не считается завершённым только потому, что создан или получил одобрение; состояние фиксируется по фактическим данным GitHub и итоговому SHA.

**Критерий готовности:** все применимые пункты отмечены и подтверждены в описании PR или связанном отчёте. Неприменимые пункты отмечаются как «не применимо» с кратким обоснованием. Невыполненный обязательный пункт блокирует запрос финального ревью; неизвестное значение не заменяется предположением.

## 4. NC-13 — определение состояний A/B/C и допустимость переходов

**Проблема:** матрица состояний версии 5 перечисляет состояния, но не задаёт формального алгоритма определения текущего состояния и не объясняет, допустим ли переход A → C без наблюдаемого состояния B.

### 4.1. Алгоритм определения состояния

Состояние определяется по фактическому содержимому `main` на одном и том же проверяемом SHA, а не по названию ветви, номеру PR или предполагаемому порядку действий:

| Состояние | Запись L-02 в `docs/decisions/README.md` | Строка L-02 в §7 основного документа | Дополнительное условие |
| --- | --- | --- | --- |
| **A** | отсутствует | открыта | оба факта проверены на одном SHA |
| **B** | присутствует со статусом `предложено` | закрыта ссылкой на запись | запись и закрытие строки проверены на одном SHA |
| **C** | присутствует со статусом `принято` | закрыта ссылкой на запись | в записи есть доказательство явного решения владельца по полному SHA |

Любая иная комбинация — например, запись отсутствует при закрытой строке, запись `предложено` при открытой строке или запись `принято` без доказательства решения — **несогласованное состояние**, а не четвёртое допустимое состояние. Применение следующей правки останавливается до устранения несогласованности.

### 4.2. Переходы

- **A → B — допустим:** отдельное разрешение владельца позволяет внести запись L-02 со статусом `предложено` и закрыть строку §7 ссылкой на неё. Оба изменения проверяются вместе на одном итоговом SHA.
- **B → C — допустим:** владелец фиксирует решение по полному SHA проверяемой версии записи; затем статус меняется на `принято` с доказательством согласования. Итоговая версия проверяется повторно.
- **A → C напрямую — не допускается как процедурный переход.** По правилам статусов сначала должна существовать проверяемая запись со статусом `предложено`; решение владельца должно относиться к конкретному полному SHA, а последующее изменение статуса создаёт новую версию, которую необходимо повторно проверить. Поэтому состояние B является обязательной промежуточной контрольной точкой, пусть даже она существует недолго.
- **Любой переход из несогласованного состояния — запрещён** до восстановления инвариантов.

**Критерий устранения NC-13:** состояние определяется воспроизводимо по двум артефактам и доказательству решения; переход A → C явно запрещён; условия A → B и B → C сформулированы.

## 5. Область и ограничения

1. Это дополнение адресует только NC-08, NC-09, NC-12 и NC-13. NC-10 и NC-11 остаются информационными и не изменяются.
2. Исторические PR #23—#31, исходный план версии 5 и отчёт адресной проверки NC-14 не редактируются. Дополнение не меняет основной документ MVP-001, `docs/decisions/README.md` или `docs/product-scope.md`.
3. Настоящий текст — предложение. Его размещение в репозитории и прохождение проверок не заменяют явного решения владельца о принятии документа.
4. Реализация NR-01 в основном документе остаётся отдельной работой и требует соответствующего разрешения. Настоящий PR не разрешает слияние сам по себе.
5. Любое последующее изменение состояния PR или `main` проверяется по фактическому полному SHA; исторические контрольные значения версии 5 не трактуются как актуальные.
