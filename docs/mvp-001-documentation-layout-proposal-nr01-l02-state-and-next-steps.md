## 3. Правила репозитория и план версии 5

### 3.1 Как фиксировать итоговый SHA записи L-02 после слияния

**Правила `main`:**

- `docs/decisions/README.md`, п. 6 (строки 68—70): «После решения владельца статус и ссылка на доказательство согласования обновляются явно, без выдумывания или заднего датирования одобрения. **Если запись обновлена новым коммитом, итоговый SHA также согласуется.**»
- `docs/decisions/README.md`, «Допустимые статусы» (строка 76): «Подтверждение должно относиться к полному SHA проверяемой версии; слияние PR само по себе не заменяет такое подтверждение, если оно требуется. **Если запись обновлена новым коммитом, прежнее подтверждение автоматически не переносится.**»
- `docs/coordination.md`, «Принятие результата», п. 4 (строки 110—111): «Владелец явно фиксирует в PR решение по итоговому SHA. До этого результат остаётся предложенным. Нет ответа — нет одобрения.»
- План версии 5, §3.1, шаги 2—3 ([PR #30][pr30]): решение владельца фиксируется в PR с записью — GitHub-ревью либо отдельным комментарием — с указанием полного SHA версии записи; после этого статус заменяется на `принято`.

**Прецедент в репозитории** (запись OQ-01—OQ-07 в `main`): подтверждение владельца в проектной переписке относится к конкретному SHA, оно «не опубликовано в GitHub и не распространяется на последующие коммиты», а слияние PR «подтверждает принятие изменений в репозиторий, но не заменяет отдельного подтверждения владельцем содержания …, если такое подтверждение требуется». Запись [PR #34][pr34] построена по тому же образцу (строки 57—59, 69—70).

**Вывод.** Запись не должна «догонять» собственный SHA: каждое её изменение создаёт новый коммит, и прежнее подтверждение на него не переносится. Практически это означает:

- **Вариант 1 (минимальный).** Слияние [PR #34][pr34] как есть. Запись в `main` сохраняет формулировку «подтверждение владельца от 2026-10-21 относится к полному SHA `b8a146da…` и не распространяется на последующие коммиты». Итоговый SHA фиксируется **в решении владельца о слиянии**: владелец указывает SHA коммита в `main`, в котором запись оказалась (коммит слияния либо SHA после слияния). Ссылка на это решение добавляется в запись отдельным PR — только по отдельному разрешению владельца, с пониманием, что сам этот коммит также не покрыт прежним подтверждением.
- **Вариант 2 (с явным покрытием итогового состояния).** Владелец формулирует решение так, что оно покрывает запись в том виде, в каком она попадёт в `main` (с указанием SHA коммита слияния и оговоркой, что редакционных изменений содержания не требуется). Тогда отдельная правка записи не нужна.
- В обоих вариантах **недопустимо** проставлять `принято` заново «по факту слияния» без явного решения владельца (п. 5; «слияние PR само по себе не заменяет такое подтверждение»).

### 3.2 Как согласовать статус записи `принято` с открытой строкой L-02 в §7 основного документа

**План версии 5, §4.3.1 ([PR #30][pr30])** задаёт матрицу состояний:

| Состояние | Запись в `docs/decisions/README.md` | Строка L-02 в §7 | Формулировка строки 6 |
| --- | --- | --- | --- |
| **A** — до шага 1 | отсутствует | открыта | (ii) |
| **B** — шаг 1 выполнен, решение владельца не зафиксировано | `предложено` | закрыта ссылкой | (iii) |
| **C** — решение владельца зафиксировано по полному SHA | `принято` | закрыта ссылкой | (i) |

Прямо указано: состояние **«запись `принято`, строка открыта» недопустимо** — «принятая запись при открытой строке воспроизводит противоречие NC-03. Поэтому шаг 1 должен давать оба изменения вместе; если этого не произошло, **применение правки 2 откладывается до устранения рассогласования**».

**Текущее состояние после слияния [PR #34][pr34] без изменения документа:** запись `принято` (строка 57) + строка L-02 в §7 открыта (строка 315 документа, статус реестра — строка 322) — то есть недопустимое состояние. Ближайшая причина: шаг 1 порядка работ (§4.1) должен был внести запись **и** закрыть строку одновременно; закрытие строки требует отдельного разрешения владельца на изменение основного документа (§3.3, §9 п. 2), которое не выдавалось.

**Способ устранения (не требует изменения статуса записи):** по отдельному разрешению владельца отдельный PR добавляет после абзаца «Статус реестра L-01—L-07» (строка 322) текст §3.3 — он «истинен в состоянии B и остаётся истинным в состоянии C, поэтому переход B → C не требует повторной правки строки». После этого состояние становится **C** (запись `принято`, строка закрыта) — допустимым, и для строки 6 применима формулировка (i).

**Последствие до устранения:** применение правки 2 (реализация NR-01) откладывается. Это совпадает с действующим запретом на начало NR-01, поэтому отдельного конфликта не создаёт — но означает, что **запуск NR-01 до закрытия строки противоречил бы плану версии 5** даже при формальном разрешении.

## 5. Как получены выводы

- Состояние `main` и PR — GitHub API (`git/ref/heads/main`, `pulls/32…35`, `pulls/*/files`, `pulls/*/commits`, `pulls/*/reviews`, `issues/*/comments`), сверка с `git rev-parse origin/main` и локальной ветвью.
- Сравнение блоков записи — `git diff` от `c03cda844…` до HEAD [PR #32][pr32] и [PR #34][pr34] с построчным сопоставлением добавленных строк.
- Зависимость по коммитам — `git merge-base` и проверка отношения предок/потомок для HEAD [PR #32][pr32] и [PR #34][pr34].
- Наличие файла доказательства в каждом HEAD — `git ls-tree -r --name-only`.
- Разрешение ссылки доказательства — приведение относительного пути `docs/decisions` + `../mvp-001-…-acceptance.md` к `docs/mvp-001-…-acceptance.md` и проверка существования в коммите.
- Конфликты при слиянии — локальное моделирование во временном worktree от `c03cda844…` (`git merge --no-ff` в отсоединённом HEAD; на удалённый репозиторий не влияет; worktree удалён, `git worktree prune` выполнен).
- Правила и план — тексты `docs/decisions/README.md` (п. 4—7, «Допустимые статусы», «Записи решений вне ADR»), `docs/coordination.md` («Принятие результата»), `CONTRIBUTING.md` (п. 9) из `main`; план версии 5 — из HEAD [PR #30][pr30] `ba206510305810bed4a70cef1d1b600b8ba821bf` (§3.1, §3.3, §4.3.1, §5, §9).

**Ограничение.** Выводы о конфликтах получены локальным моделированием средствами git, а не через GitHub: GitHub computed `mergeable` только для текущего состояния, где оба PR ещё `clean`. Фактическое поведение GitHub после слияния одного из PR может отличаться в деталях сообщений, но конфликт содержимого в одном файле воспроизводится детерминированно.
