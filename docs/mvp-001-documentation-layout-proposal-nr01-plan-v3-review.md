## 6. Замечания

### NC-06 · Среднее · Не определены условия применимости вариантов строки 6

**Доказательство.** План называет вариант (i) основным, а вариант (ii) резервным, но не задаёт условий, при которых каждый из них истинен.

- Вариант (i) утверждает: «Полные отчёты ревью и операционные отчёты хранятся в связанных PR — **по решению владельца** по вопросу L-02 (раздел 7, вариант (а))» и отсылает к записи решения в файле `docs/decisions/README.md`. По §3.1 плана запись вносится со статусом `предложено` и переводится в `принято` только после явного решения владельца по полному SHA. Порядок работ (§4.1) не требует, чтобы этот перевод произошёл до шага 2. Следовательно возможна последовательность: запись внесена со статусом `предложено` → применён вариант (i) → документ утверждает «по решению владельца», а реестр решений числит запись неподтверждённой. Это противоречие того же типа, что NC-03.
- Вариант (ii) утверждает: «порядок применён по указанию владельца, решение по вопросу L-02 (раздел 7) **подлежит отдельной фиксации**». Шаг 1 закрывает строку L-02 в §7. Если шаг 1 выполнен, утверждение становится неточным: вопрос уже закрыт в документе.

**Вывод.** Дефект не в текстах вариантов, а в отсутствии условий их выбора: при любой последовательности шагов 1 и 2 один из вариантов рискует стать неточным.

**Рекомендация.** Добавить в §4.3 явные условия:

- вариант (i) применяется только после внесения записи **и** перевода её в статус `принято` (явное решение владельца по полному SHA);
- вариант (ii) применяется, только если строка L-02 в §7 ещё не закрыта;
- для промежуточного состояния (строка закрыта, запись ещё `предложено`) требуется третья формулировка, не утверждающая принятия, — например: «Полные отчёты ревью и операционные отчёты хранятся в связанных PR; вопрос L-02 закрыт (раздел 7), статус записи решения — в файле `docs/decisions/README.md`».

**Критерий устранения.** Для каждого сочетания состояний (запись `предложено` / `принято`; строка §7 открыта / закрыта) в плане существует применимая и истинная формулировка строки 6.

### NC-07 · Среднее · Правка 6 не упоминает NR-01 — замечание, которое эта же правка устраняет

**Доказательство.** Моделирование даёт итоговую строку 4:

```markdown
**Дата:** 2026-10-21 (UTC). **Редакция:** 3 — устранены замечания RC-01—RC-03 и C-01—C-05 независимого ревью, а также FR-01—FR-05 повторного ревью и TR-01 третьего ревью.
```

Правка, вносящая эту формулировку, сама является устранением NR-01 — замечания [PR #20][pr20] о неполном учёте ревью. В перечне NR-01 отсутствует; NR-02 отсутствует обоснованно (оно не устраняется и классифицировано как информационное). Дополнительно: дата в строке 4 остаётся прежней, тогда как правка может быть внесена позже; план не указывает, обновляется ли дата.

**Вывод.** Заголовок документа будет перечислять устранённые замечания, исключая то, которое устраняется этой же правкой. Поскольку суть NR-01 — неполный учёт истории в самом документе, возникает неполнота того же класса.

**Рекомендация.** Одно из двух:

- **(а)** дополнить строку 4: «… и TR-01 третьего ревью, а также NR-01 повторного ревью исправления (учёт ревью и таблица этапов); NR-02 не устраняется»;
- **(б)** оставить строку 4 без изменений (тогда TR-01 в перечне также не упоминается, но его устранение описано строкой таблицы этапов, а краткая история остаётся восстановимой).

В обоих случаях явно решить вопрос с датой в строке 4.

**Критерий устранения.** После применения правки строка 4 не содержит утверждения, которое станет неточным из-за самой правки; вопрос даты решён явно.

### NC-08 · Низкое · ПТ-1 не определяет понятие «этап»

**Доказательство.** ПТ-1, п. 1: «каждая содержательная правка документа добавляет одну строку». При этом строка 5 объединяет два события: исправление TR-01 (коммит `9f203708…`, изменение содержимого) и слияние (содержимое не изменилось: дерево `5bc9dce7…` идентично дереву `main`). Кроме того, шаг 1 порядка работ также изменяет документ (§7) — план не указывает, считается ли это этапом и кто добавляет для него строку.

**Вывод.** Правило допускает два разных прочтения; при применении это приведёт к расхождению между исполнителями.

**Рекомендация.** Определить «этап» как **изменение содержимого документа**; тогда:

- строка 5 называется «Исправление TR-01», а упоминание слияния переносится в её описание (сейчас слияние вынесено в заголовок);
- либо, если владелец предпочитает считать этапом событие истории, — тогда слияние и правка §7 должны получать отдельные строки, что противоречит минимальности.

Явно указать, что правка §7 из шага 1 считается этапом и получает строку следующим изменением.

**Критерий устранения.** Правило однозначно для трёх случаев: правка содержимого, слияние без изменения содержимого, закрытие строки реестра.

### NC-09 · Низкое · Два утверждения в проекте записи требуют уточнения

**Доказательство.**

1. Диапазон «ревью в PR #19—#25 — 0» верен для указанных PR, но уже неполон: существует [PR #26][pr26] (ревью — 0; комментарии — только `sourcery-ai[bot]`), и к моменту внесения записи могут появиться следующие. Проверено: ревью в [PR #19][pr19]—[PR #26][pr26] — 0; комментариев владельца нет.
2. Формулировка «Варианты (б) и (в) не применяются» — вывод из утверждённого варианта (а); буквально владелец формулировал выбор варианта (а) и дополнение о ссылках, а не отклонение остальных.

**Вывод.** Оба утверждения истинны в момент подготовки, но первое неизбежно устареет, а второе выходит за пределы буквально подтверждённого.

**Рекомендация.** Заменить диапазон номеров на формулировку без номеров: «в GitHub нет отдельного решения владельца по полному SHA: ревью в связанных PR отсутствуют, комментарии оставлены только автоматическим ботом». Вторую формулировку либо подтвердить у владельца, либо заменить на «применяется вариант (а)».

**Критерий устранения.** Каждое утверждение записи либо подтверждено документально, либо сформулировано нейтрально и не зависит от будущих номеров.

### NC-10 · Информационное · Характер записи против преамбулы раздела

**Доказательство.** `docs/decisions/README.md` (строки 9—11) определяет ADR как запись значимого архитектурного или продуктового решения. L-02 — документационное соглашение о хранении ревью. Прецеденты раздела включают как продуктовые (OQ-01—OQ-07), так и процессные (BOOTSTRAP-001) записи, поэтому размещение допустимо; характер записи при этом отличается от описанного в преамбуле.

**Вывод.** Маршрут A утверждён владельцем и выполнен корректно; различие носит характер уточнения, а не нарушения.

**Рекомендация.** Явно указать в тексте записи, что речь идёт о документационном соглашении (слова «хранение независимых ревью в репозитории» в заголовке уже задают характер), либо подтвердить размещение отдельным решением владельца.

### NC-11 · Низкое · Альтернативный вариант закрытия строки не обеспечен текстом

**Доказательство.** Строка 322 допускает два способа. План содержит текст только для закрытия ссылкой (§3.3). Проверка варианта переноса (§5.2) показала, что он требует изменения преамбулы раздела (строка 35) либо создания нового подраздела, а раздел «Вопросы для владельца» для закрытого вопроса не применим (строка 189).

**Вывод.** Вариант переноса существенно инвазивнее, чем следует из формулировки строки 322; его отсутствие в плане не является дефектом, но делает выбор владельца недостаточно обоснованным документально.

**Рекомендация.** Либо зафиксировать в плане отказ от варианта переноса с приведённым обоснованием, либо подготовить для него текст.

**Критерий устранения.** Оба способа из строки 322 либо обеспечены текстом, либо обоснованно исключены в самом плане.

### NC-12 · Низкое · Нет сводного критерия готовности реализующего PR

**Доказательство.** План содержит критерий устранения NC-01 (команда проверки инварианта ссылок) и правила ПТ-1, ПТ-2, но не содержит сводного перечня проверок после применения правок: сверка инварианта ссылок, число колонок таблицы (4), разрешимость относительных ссылок, отсутствие утверждения об исчерпывающести перечня ревью, соответствие ПТ-1 и ПТ-2, отсутствие самоссылки. Форма задачи в `docs/coordination.md` предусматривает разделы «Критерии готовности» и «План проверок».

**Вывод.** План применим, но не даёт исполнителю проверяемого перечня; при реализации часть проверок может быть пропущена.

**Рекомендация.** Добавить раздел «Критерии готовности» с перечисленными проверками и ожидаемыми результатами.

**Критерий устранения.** Реализующий PR содержит воспроизводимый перечень проверок и фиксирует их результаты.
