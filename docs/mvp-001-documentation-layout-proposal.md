## 2. Существующая структура `docs/`

Фактическое дерево на контрольном SHA:

```
docs/
├── coordination.md                       132 строки   процессный регламент
├── decisions/
│   └── README.md                         126 строк    реестр решений + порядок ведения ADR
├── mvp-001-user-scenario-acceptance.md   168 строк    AC-01—AC-08, T-01—T-13, OQ-01—OQ-07
├── product-scope.md                      317 строк    границы продукта + реестр статусов решений
└── technical/
    └── TECH-DESIGN-001.md               1214 строк    архитектурное предложение и технический отчёт
```

Установлено:

- В `docs/` существует **только два** подкаталога: `docs/decisions/` (выделен по функции — записи решений) и `docs/technical/` (выделен по типу документа).
- Каталог `docs/mvp-001/` **отсутствует**.
- Имена файлов проверены по всем деревьям истории по шаблонам `review`, `proposal`, `report`, `ревиз`, `предложен`, `отчёт`. **Число совпадений зависит от контрольного SHA** и увеличивается при каждом добавлении в `docs/` файла, имя которого содержит один из шаблонов. Сводка по контрольным SHA и команда пересчёта — в разделе 2.1; утверждение о числе совпадений без указания SHA в документе не используется.
- Инвариант, не зависящий от последующих правок: во всех деревьях коммитов, **предшествующих `e192275…`** (первая публикация документа), совпадений по указанным шаблонам не было ни одного. Термин «independent review» в именах файлов не встречается; в сообщении коммита [PR #13][pr13] он присутствует.

Именно так построена формулировка потому, что вторая редакция утверждала «единственное совпадение … во всех деревьях истории, включая текущее» и стала ложной, когда тот же PR добавил отчёт об устранении замечаний с `review` в имени. Привязка результата к контрольному SHA исключает повторение ошибки: результат пересчитывается, а не предполагается.

### 2.1. Объём истории и воспроизводимость проверки

Первая редакция этого документа утверждала: «за всю историю репозитория (2 коммита, все деревья)». Утверждение ошибочно по двум причинам: история содержала не два коммита, а одиннадцать; рабочая копия была **мелким клоном** с усечённой историей, из которой объём истории не виден. Вывод о «всей истории» был сделан по неполной выборке.

Фактические объёмы по полной копии (`git fetch --unshallow origin`):

| Точка отсчёта | Достижимо коммитов |
| --- | --- |
| Контрольный SHA `main` `f0253e54…` | **11** |
| Коммит `e192275…`, впервые опубликовавший этот документ | **12** |

Воспроизводимые команды:

```bash
git rev-parse --is-shallow-repository                          # → true в исходной копии: история усечена
git fetch --unshallow origin                                   # раскрыть историю до полной
git rev-list --count f0253e54dfdbc8e5ce47679ef2c4cfc7adcbc4cf   # → 11
git rev-list --count e192275560ac0e67f003bd520aab5ad37f265aa7   # → 12
```

Проверка имён файлов по всем деревьям всех коммитов. Контрольный SHA задаётся явно: результат пересчитывается при каждом добавлении файла в `docs/`.

```bash
SHA=$(git rev-parse HEAD)                 # либо задайте контрольный SHA явно
git rev-parse --is-shallow-repository     # → false; до раскрытия клона проверка недостоверна
for c in $(git rev-list "$SHA"); do
  git ls-tree -r --name-only "$c"
done | sort -u > /tmp/paths.txt
echo "путей: $(wc -l < /tmp/paths.txt)"
echo "совпадений: $(grep -icE 'review|proposal|report|ревиз|предложен|отчёт' /tmp/paths.txt)"
grep -iE 'review|proposal|report|ревиз|предложен|отчёт' /tmp/paths.txt
```

Результат по контрольным SHA:

| Контрольный SHA | Уникальных путей | Совпадений | Совпадающие пути |
| --- | --- | --- | --- |
| `e192275…` — первая публикация документа | 11 | **1** | `docs/mvp-001-documentation-layout-proposal.md` |
| `a7b6f4e…` — публикация отчёта об устранении замечаний | 12 | **2** | `docs/mvp-001-documentation-layout-proposal.md`; `docs/mvp-001-documentation-layout-proposal-review-response.md` |
| коммит настоящей редакции (SHA — `git rev-parse HEAD`) | 13 | **3** | те же два и `docs/mvp-001-documentation-layout-proposal-review-response-followup.md` |

Правила, исключающие повторение прежней ошибки:

1. Утверждение о числе совпадений действительно **только для указанного контрольного SHA**; число без SHA не приводится.
2. Любой новый файл в `docs/`, имя которого содержит `review`, `proposal`, `report`, `ревиз`, `предложен` или `отчёт`, увеличивает число совпадений; перед публикацией такого файла таблица и вывод команды пересчитываются.
3. Формулировка «в истории не существовало ни одного файла с таким именем» допустима только с явной границей: «во всех коммитах, предшествующих `e192275…`».

Вывод о количестве коммитов допустим только после раскрытия клона и только с указанием точки отсчёта: при HEAD `280f903…` мелкий клон давал 1 вместо 10 — из этой точки достижимо 10 коммитов; из `main` `f0253e54…` достижимо 11.

## 3. Действующие соглашения и правила

### 3.1. Соглашения об именовании

Собранные по фактическим именам файлов и тексту правил:

| Стиль | Пример | Где зафиксирован |
| --- | --- | --- |
| Нижний регистр, kebab-case, плоско в `docs/` | `docs/coordination.md`, `docs/product-scope.md` | фактические имена |
| Префикс области `mvp-001-`, плоско в `docs/` | `docs/mvp-001-user-scenario-acceptance.md` | фактическое имя — **установленное соглашение для документов MVP-001** |
| Верхний регистр + числовой ID, в подкаталоге по типу | `docs/technical/TECH-DESIGN-001.md` | фактическое имя |
| ADR: `N-short-title.md`, где `N` — номер отдельного Issue | `docs/decisions/<N>-short-title.md` (шаблон; `N` назначает GitHub и вручную не вычисляется) | `docs/decisions/README.md`, раздел «Порядок ведения», п. 1 |

Пример ADR приведён в виде заполнителя `<N>`, а не с конкретной цифрой: номера 3 и 4 в этом репозитории уже заняты ([PR #3][pr3] и [Issue #4][issue4] — GitHub нумерует Issues и PR в общем пространстве), поэтому цифра в шаблоне могла бы быть прочитана как уже назначенный номер. ADR-файлов в `docs/decisions/` пока нет — существует только `README.md`, — следовательно никакая нумерация не затронута.

Прямого документа, регламентирующего именование файлов вне ADR, в репозитории **нет**. Соглашения восстанавливаются по фактическим именам и по правилам ADR.

### 3.2. Правила размещения по каналам

`docs/coordination.md`, раздел «Каналы и источник истины»:

| Канал | Назначение по документу |
| --- | --- |
| Discussion №1 | координация, вопросы, краткие итоги, ссылки. «Не замена очереди задач или документации» |
| Issues | конкретные задачи с целью, границами и критериями готовности; канонический ID — номер Issue |
| Pull requests | изменения, команды проверок, результаты, **ревью** и решение владельца по полному SHA |
| Документация репозитория | **правила и записи решений**; «предложенные документы явно помечаются» |

Ключевые следствия:

1. **Ревью по правилам — артефакт PR**, а не отдельный файл документации.
2. **Предложенные документы допустимы в репозитории**, но должны явно помечаться как предложения.
3. `docs/decisions/README.md`: «Обычные задачи и **технические отчёты остаются в Issues и PR**». При этом `docs/technical/TECH-DESIGN-001.md` — технический отчёт, хранящийся в репозитории. Правило и фактическая практика **расходятся**; TECH-DESIGN-001 является единственным прецедентом-исключением.

### 3.3. Правила статусов и решений

`docs/decisions/README.md`, раздел «Порядок ведения»:

- до явного решения владельца статус — `предложено`;
- для каждого нового ADR согласуется **отдельный Issue**; номер «следующий» не вычисляется вручную;
- перед созданием файла проверяется каталог и открытые PR по этому Issue; один Issue — один ADR — один активный PR;
- допустимые статусы: `предложено`, `принято`, `отклонено`, `заменено`; последние три требуют ссылки на явное решение владельца;
- подтверждение относится к полному SHA; слияние PR не заменяет подтверждение;
- номера ADR задним числом не назначаются;
- **автоматического контроля уникальности нет** — всё проверяется вручную.

### 3.4. Требования к изменениям документации

- Изменения вносятся через PR, в выделенной ветке, не в `main` (`CONTRIBUTING.md`, п. 3).
- «Не меняйте одни и те же файлы параллельно с другим исполнителем без согласования».
- Документационные задачи не изменяют код приложения, зависимости и инфраструктуру без отдельного разрешения.
- PR содержит полный commit SHA версии для ревью; решение владельца относится к полному SHA.
- В файлы, историю Git, Issues, Discussion, PR, логи, отчёты, скриншоты и вложения **не допускаются** секреты, персональные данные и реальные данные детей; только синтетические данные.
- Процессные документы пишутся по-русски (`README.md`, раздел «Documentation»).

## 4. Оценка предложенной структуры `docs/mvp-001/`

Предложенная структура:

```
docs/mvp-001/
├── proposals/
├── reviews/
├── reports/
└── decisions/
```

**Общий вывод: структура в предложенном виде не рекомендуется.** Три из четырёх элементов конфликтуют с действующими соглашениями либо дублируют существующие каталоги. Ниже — по каждому элементу.

### 4.1. `docs/mvp-001/decisions/` — конфликт, не создавать

**Проблема.** `docs/decisions/` уже существует и является единственным каталогом записей решений, с собственным порядком ведения, шаблоном ADR и правилом «один Issue — один ADR — один активный PR». Создание второго каталога решений:

- разделяет реестр решений на два места, разрушая единственную точку контроля;
- ломает ручную проверку «перед созданием файла проверьте каталог и открытые PR по этому Issue» — проверять придётся два каталога;
- создаёт риск двух файлов с одним и тем же `ADR-N`, что `docs/decisions/README.md` прямо называет конфликтом, блокирующим работу.

**Рекомендация.** Не создавать. Записи решений размещать в `docs/decisions/` по действующему порядку.

### 4.2. `docs/mvp-001/` как каталог — конфликт с префиксным соглашением

**Проблема.** Документы области MVP-001 уже именуются префиксом: `docs/mvp-001-user-scenario-acceptance.md`. Одновременное существование `docs/mvp-001-user-scenario-acceptance.md` и каталога `docs/mvp-001/` порождает две параллельные конвенции для одной области: файлы одной тематики оказываются в разных местах, а поиск и навигация становятся неоднозначными.

**Рекомендация.** Выбрать одну конвенцию и зафиксировать её решением владельца. Варианты — в разделе 5.

### 4.3. `reports/` — противоречит правилу, допустимо только как исключение

**Проблема.** `docs/decisions/README.md` прямо устанавливает: «Обычные задачи и технические отчёты остаются в Issues и PR». Размещение отчётов о восстановлении и проверке файлов в каталоге документации противоречит этой формулировке.

**Нюанс.** В репозитории есть прецедент-исключение: `docs/technical/TECH-DESIGN-001.md` — технический отчёт, сохранённый как файл. Следовательно, правило не абсолютно, но исключение требует обоснования: отчёт должен быть долговечным справочным документом, а не операционной сводкой.

**Рекомендация.** Операционные отчёты (восстановление файлов, разовые проверки) оставлять в Issues/PR. В документацию выносить только долговечные отчёты — по прецеденту `docs/technical/`.

### 4.4. `reviews/` — пробел в структуре, но новое соглашение

**Проблема.** Каталог для независимых ревью в репозитории отсутствует, и до публикации настоящего PR файлов независимых ревью в репозитории не было: ревью по правилам — артефакт PR. Отчёт об устранении замечаний, добавленный этим же PR, независимым ревью не является: это ответ автора на замечания ревью. При этом независимое ревью, замечания которого были устранены в [PR #13][pr13], не сохранено в репозитории: воспроизвести его содержание по репозиторию невозможно.

**Оценка.** Это реальный пробел, а не нарушение правила. Создание `reviews/` допустимо, но вводит новое соглашение и потому требует отдельного решения владельца.

## 5. Рекомендуемые пути по типам документов

### 5.1. Рекомендуемый вариант (минимальный, без новых каталогов)

Использует уже существующие соглашения; не создаёт каталогов; не требует решения владельца о новой структуре.

| Тип документа | Рекомендуемый путь | Обоснование |
| --- | --- | --- |
| Предложение стартового контента | `docs/mvp-001-starter-content-proposal.md` | Плоский файл с префиксом `mvp-001-` — прямое продолжение соглашения `docs/mvp-001-user-scenario-acceptance.md`. Допустимость предложенных документов подтверждена `docs/coordination.md`: «предложенные документы явно помечаются». Путь указан для **базового имени без суффикса версии**: суффикс `-v2` в имени `MVP-001-starter-content-proposal-v2.md` возник во внешней среде и соглашением репозитория не является (варианты — L-07) |
| Независимое ревью | `docs/mvp-001-starter-content-proposal-review.md` (при сохранении в репозитории) либо PR + Issue | Плоский файл рядом с рецензируемым документом. Первичный канал по правилам — PR; файл оправдан как долговечная запись для ревью, проведённых вне PR-потока |
| Технические отчёты (долговечные) | `docs/technical/<ИМЯ>-<NNN>.md` | Прецедент `docs/technical/TECH-DESIGN-001.md`: подкаталог по типу, верхний регистр, числовой ID |
| Технические отчёты (операционные) | Issue или PR, без файла | `docs/decisions/README.md`: «технические отчёты остаются в Issues и PR» |
| Открытые вопросы | `docs/product-scope.md` | Реестр уже ведётся там: OQ-01—OQ-07, C-01, A-01/A-02, P-01—P-07, M-01—M-07, U-01—U-06. Разделение реестра нежелательно |
| Принятые решения | `docs/decisions/N-short-title.md` (ADR) и `docs/decisions/README.md` (записи вне ADR) | Действующий порядок ведения; отдельный Issue на каждый ADR |

### 5.2. Альтернативный вариант (один каталог, если владелец предпочитает группировку)

Если владелец выберет группировку по области, рекомендуется **один** каталог без вложенного `decisions/`:

```
docs/mvp-001/
├── mvp-001-starter-content-proposal.md     предложение
├── mvp-001-starter-content-review.md       независимое ревью
└── (долговечные отчёты при необходимости)
```

Условия применения:

- каталог `decisions/` внутри `docs/mvp-001/` **не создаётся**;
- либо все документы MVP-001 переносятся в каталог единовременно (включая `mvp-001-user-scenario-acceptance.md`), либо сохраняется только префиксная конвенция. Смешивание двух конвенций не рекомендуется;
- перенос существующего файла — отдельная задача с отдельным PR и решением владельца.

### 5.3. Сводка по предложенной структуре

| Элемент | Оценка | Решение |
| --- | --- | --- |
| `docs/mvp-001/proposals/` | Избыточно при одном-двух документах; дублирует префиксную конвенцию | Не создавать; использовать `docs/mvp-001-starter-content-proposal.md` |
| `docs/mvp-001/reviews/` | Закрывает реальный пробел; новое соглашение | Требует решения владельца; при согласии — допустимо |
| `docs/mvp-001/reports/` | Противоречит правилу «технические отчёты остаются в Issues и PR» | Не создавать; исключение — только долговечные отчёты в `docs/technical/` |
| `docs/mvp-001/decisions/` | Конфликт с существующим `docs/decisions/` | **Не создавать** |

### 5.4. Проверка пути для этого отчёта

Путь `docs/mvp-001-documentation-layout-proposal.md`:

- каталог `docs/` **существует** — условие «если каталог отсутствует, не создавать» выполняется, создавать каталог не требуется;
- имя соответствует префиксному соглашению `mvp-001-*.md` — конфликта с действующими правилами нет;
- документ не является ADR, поэтому требование об отдельном Issue для ADR к нему не применяется;
- статус `предложено` соответствует `docs/decisions/README.md`.

Путь отчёта об устранении замечаний — `docs/mvp-001-documentation-layout-proposal-review-response.md`: тот же каталог `docs/`, тот же префикс `mvp-001-`, имя образовано от имени проверяемого документа. Новый каталог не требуется, соглашение не нарушается.

**Ссылки на задачи.** По `CONTRIBUTING.md`, раздел «Регистрация и идентификация задач», в ссылках указывается номер Issue или полный URL, а номер не подменяется заголовком или самовольно введённым ID. В этой редакции все упоминания Issues и PR оформлены ссылками на полные URL; определения — в конце документа.

**Связь с задачей.** Работа выполняется в ветке, закреплённой за сессией, в рамках [Issue #4][issue4] (MVP-001, OPEN, 0 комментариев). Размещение документации не заявлено в границах этой задачи явно; `CONTRIBUTING.md`, п. 1 раздела «Порядок выполнения задачи», ожидает для каждой задачи Issue с целью, исходным SHA, границами и критериями. Оформление отдельного Issue под задачу размещения документации либо явное расширение объёма [Issue #4][issue4] — решение владельца; настоящее предложение его не предрешает.

## 7. Открытые вопросы для владельца

| ID | Вопрос | Варианты | Последствия | Кто решает |
| --- | --- | --- | --- | --- |
| L-01 | Конвенция группировки документов MVP-001 | (а) префикс `mvp-001-*` плоско в `docs/`; (б) единый каталог `docs/mvp-001/` с переносом всех файлов; (в) смешанно | (а) ничего менять не нужно, но при росте числа документов каталог переполняется; (б) наглядная группировка, нужен отдельный PR на перенос; (в) неоднозначность навигации | Владелец |
| L-02 | Хранение независимых ревью в репозитории | (а) только в PR; (б) файл рядом с рецензируемым документом; (в) отдельный каталог `reviews/` | (а) соответствует правилам, но содержание ревью теряется (прецедент PR #13); (б)/(в) сохраняемость, но новое соглашение | Владелец |
| L-03 | Допустимость исключения для технических отчётов | (а) строго по правилу — в Issues и PR; (б) долговечные отчёты — в `docs/technical/` по прецеденту TECH-DESIGN-001 | (а) единообразие, потеря справочного материала; (б) сохраняемость, но размывает правило | Владелец |
| L-04 | Устранение расхождения правила и практики | `docs/decisions/README.md` («технические отчёты остаются в Issues и PR») против существования `docs/technical/TECH-DESIGN-001.md` | Сохраняющаяся двусмысленность при каждом решении о размещении | Владелец |
| L-05 | Регистр и формат имён для новых отчётов | (а) верхний регистр + числовой ID (`TECH-DESIGN-001`); (б) нижний регистр + префикс области | Единообразие имён в `docs/technical/` | Владелец |
| L-06 | Фиксация контрольных сумм документов | Обязательная фиксация SHA-256 при создании документа | Без этого идентичность восстановленных копий недоказуема (практическая проблема, уже приведшая к утрате доказуемости) | Владелец |
| L-07 | Суффикс версии в имени документа | (а) версия фиксируется только в теле документа, имя остаётся базовым; (б) суффикс `-v2` допускается в имени файла | (а) имя стабильно, версия видна в документе; (б) версия видна в списке файлов, но имя меняется при каждой версии и рассредоточивает историю документа по нескольким именам | Владелец |

**Статус реестра L-01—L-07.** Реестр временный: это вопросы, порождённые настоящим предложением и вынесенные на решение владельца. Он **не является** вторым постоянным реестром открытых вопросов и не отменяет рекомендацию раздела 5.1 хранить открытые вопросы в `docs/product-scope.md`. После решения владельца вопросы переносятся в `docs/product-scope.md` либо закрываются ссылкой на решение.

**L-02 закрыт.** Выбран вариант (а): полные независимые ревью и операционные отчёты хранятся в отдельных PR, при сохранении необходимых ссылок и краткой истории в основном документе. Вариант выбран владельцем 2026-10-21; строка закрыта по его разрешению. Запись решения — в [записях решений](decisions/README.md); статус записи указан там же и повышается только по явному решению владельца по полному SHA (`docs/decisions/README.md`, п. 5—6). Строка сохранена в таблице выше как запись вопроса и решения по нему.
