## 2. Решения владельца: подтверждённое и заявленное

### 2.1. Уровни подтверждения

План различает четыре уровня:

1. **Текст решения, опубликованный владельцем в GitHub** — ревью, комментарий, Issue или Discussion, авторство которых принадлежит владельцу. Такой текст проверяется по API и не требует пересказа.
2. **Содержание принятого и слитого документа** — запись решения, отчёт или документ в `main`, внесённый PR, слитым владельцем. Подтверждает наличие и содержание текста в `main`, но не заменяет публикацию решения владельцем, если она требуется правилами репозитория.
3. **Заявлено без первичного текста** — утверждение о решении владельца присутствует только в более раннем документе или отчёте.
4. **Предложение** — правило или формулировка предложены, но владельцем не утверждены.

Для L-02 установлено: текст решения в GitHub владельцем **не опубликован** — в [PR #19][pr19]—[PR #36][pr36] нет ревью и комментариев `Kvasha62`; [Issue #4][issue4] содержит 0 комментариев; в Discussion #1 есть один комментарий владельца от 2026-10-20, не относящийся к L-02. Дословная цитата решения существует только внутри записи L-02 — документа, внесённого [PR #34][pr34], то есть на уровне 2.

Утверждения уровней 3—4 не используются в версии 6.1 как установленные правила и не расширяются. Уровень 2 используется только как содержание документа: он подтверждает текст в `main`, но не заменяет опубликованный акт решения владельца.

## 4. Определение состояния L-02 и выбор формулировки (NC-13)

### 4.1. Два разных сведения

Состояние L-02 определяется двумя независимыми сведениями, которые нельзя подменять одно другим:

1. **Наличие доказательства решения владельца** — дословная цитата решения, дата и полный 40-символьный SHA версии, к которой решение относится.
2. **Текстовый статус записи** — значение `предложено`, `принято`, `отклонено` или `заменено` в `docs/decisions/README.md`.

Статус `принято` без доказательства не образует состояние C. Доказательство без повышенного статуса не образует состояние C и не даёт исполнителю права повысить статус самостоятельно.

### 4.2. Процедура определения

1. Зафиксировать полный SHA `main`, дату и время проверки.
2. Прочитать `docs/decisions/README.md` на этом SHA: наличие записи L-02, её текстовый статус, наличие цитаты решения и полного SHA в доказательстве.
3. Прочитать основной документ на том же SHA: состояние строки L-02 в §7 и применяемую формулировку строки 6.
4. Сопоставить сведения с таблицей §4.3.
5. Если комбинация не входит в таблицу — остановиться по правилу §4.5.
6. Зафиксировать результат: состояние, применимая формулировка, SHA и время проверки.

Все три чтения выполняются на **одном и том же** SHA. Смешивать документы с разных коммитов запрещено.

| Состояние | Запись L-02 | Доказательство решения | Строка L-02 в §7 | Применимая формулировка строки 6 |

### 4.4. Недопустимые комбинации

Не являются четвёртым состоянием и блокируют применение правки:

- запись отсутствует, строка закрыта;
- статус `принято` без доказательства решения;
- статус `принято` с доказательством, но строка открыта;
- статус `предложено`, но строка открыта;
- статус `отклонено` или `заменено` — вне матрицы; требует отдельного решения владельца.

### 4.5. Порядок при расхождении

| Расхождение | Действие |
| --- | --- |
| **D1.** Статус `принято`, доказательства нет | Не считать состоянием C. Остановиться; не применять формулировку (i); сообщить владельцу; изменение статуса — только владелец |
| **D2.** Статус `предложено` (доказательство может присутствовать или отсутствовать) | Если строка §7 закрыта — текстовое состояние B; формулировка (iii) истинна, поскольку не утверждает значения статуса. ### 4.6. Полномочия

- Исполнитель **не вправе** менять статус записи L-02, добавлять доказательство, удалять запись или создавать её заново.

### 4.7. Момент определения

Формулировка выбирается по проверенному состоянию целевой базы **непосредственно перед реализацией**. Результаты более ранних проверок, включая проверки версий 1—6 и отчёты ревью, доказательством текущего состояния не являются. Перед применением правки повторяются шаги §4.2; в отчёте указываются SHA, дата и время.

### 6.4. Ретроспективное применение к PR #38

**Два уровня оценки.** Для каждого критерия раздельно фиксируются:

1. **Документальная (механическая) проверка** — что именно проверено по файлам, Git-объектам или данным GitHub: `выполнена, нарушений не выявлено`, `выявлено нарушение` или `не выполнялась`.
2. **Итоговый статус критерия** — одно из трёх значений: `пройден`, `не пройден`, `не проверен`.

Правила присвоения итогового статуса:

- `пройден` — критерий выполнен целиком: документальная проверка выполнена без нарушений **и** все обязательные условия критерия выполнены;
- `не пройден` — документальная проверка выявила нарушение критерия;
- `не проверен` — обязательное условие критерия не может быть установлено по доступным данным: нет первичного текста решения владельца, нет утверждённого правила, нет текста разрешения либо доказательство недоступно.

Документальная проверка сама по себе не делает критерий пройденным. Если критерий содержит обязательное условие, которое не выполнено, его итоговый статус — `не проверен`, даже когда проверяемая часть документа нарушений не содержит. Статус не заменяется предположением и не выводится «по смыслу».
