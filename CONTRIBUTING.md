# Участие в разработке

## Статус

Документ предложен в [BOOTSTRAP-001]. До явного утверждения владельцем
итогового commit SHA bootstrap остаётся предложением. Разрешение подготовить
изменения не означает их принятие. Исходные ограничения безопасности из
[README](README.md) действуют независимо от согласования новых документов.

Bootstrap включает только документацию и шаблоны. Не добавляйте код
приложения и не выбирайте стек, архитектуру или состав MVP в этой задаче.
Открытые требования собраны в [границах продукта](docs/product-scope.md).

## Порядок выполнения задачи

1. Создайте Issue с ID, целью, исходным состоянием, полным commit SHA,
   границами изменений, ограничениями и проверяемыми критериями готовности.
2. Согласуйте объём с владельцем. Отделите утверждённые требования от гипотез.
   Неясности и новые продуктовые решения вынесите на согласование.
3. Работайте в выделенной ветке, не в `main`. Если среда закрепляет рабочую
   ветку за сессией, используйте именно её. Не меняйте одни и те же файлы
   параллельно с другим исполнителем без согласования.
4. Подготовьте минимальные изменения в согласованных границах. Свяжите один
   PR с задачей; изменение объёма требует отдельного согласования.
5. Выполните применимые проверки. Укажите точные команды, версии разовых
   инструментов, результаты и причины невыполненных проверок.
6. Зафиксируйте изменения и получите полный SHA командой
   `git rev-parse HEAD`. Представьте PR с отчётом по этому SHA.
7. Запросите техническое ревью и отдельное решение владельца. До решения
   результат имеет статус «предложено / на ревью», а не «принято».
8. Новые коммиты требуют актуального отчёта, повторной проверки изменённой
   части и подтверждения итогового SHA. Старое ревью относится к старому SHA.
9. Слияние выполняется только по явному решению владельца. Не включайте
   автоматическое слияние. Утверждение bootstrap не утверждает будущие
   продуктовые задачи или технологический стек.

Подробные роли и форматы сообщений: [протокол](docs/coordination.md).

## Ревью и утверждение

Ревью содержит ссылку на PR, полный commit SHA и конкретные замечания или
вывод. Отсутствие замечаний не заменяет решение владельца.

Владелец явно указывает решение и полный SHA в PR: через GitHub review,
если это доступно, либо отдельным комментарием. Автор PR или агент не должен
выдавать собственный отчёт за утверждение владельца. При общей учётной
записи источник сообщения обязательно подписывается.

Этот документ не настраивает branch protection, обязательные проверки или
CI: это правила процесса, а не заявление о технически включённых запретах.

## Проверки документационного PR

Проверьте рабочие и подготовленные изменения:

```bash
git diff --check
git diff --cached --check
```

После коммита проверьте весь PR относительно актуального `origin/main`:

```bash
git diff --check origin/main...HEAD
git diff --name-status origin/main...HEAD
git rev-parse HEAD
git status --short
```

Дополнительно проверьте Markdown, существование целей относительных ссылок
и корректность YAML формы задачи. Если применяете разовый валидатор,
укажите его версию и команду в PR; это не выбор стека приложения.

На этапе bootstrap нет приложения, сборки, тестов или CI. Не заявляйте об
их успешном выполнении. Пишите «не запускалось» с причиной. Чистый Git diff
и корректные документы не являются тестированием продукта.

После изменения проверяемых файлов повторите применимые проверки и
обновите SHA отчёта. Не публикуйте необработанные логи с чувствительными
данными.

## Безопасность

- Запрещены секреты, пароли, токены и любые персональные данные, особенно
  реальные данные детей. Не включайте их в файлы, историю Git, Issues,
  Discussion, PR, логи, отчёты, скриншоты и вложения.
- В примерах и проверках используйте только синтетические данные.
  Маскирование реальных данных само по себе не делает их допустимыми.
- Не добавляйте материалы без необходимых прав.
- Удаление данных, изменение production, платные операции и другие
  рискованные действия требуют отдельного явного разрешения владельца.
- При обнаружении секрета остановите публикацию; не цитируйте его повторно.
  Сообщите владельцу без значения секрета для отзыва и безопасного удаления.
