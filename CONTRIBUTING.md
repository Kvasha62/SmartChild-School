# Участие в разработке

## Статус

Документ принят в составе [BOOTSTRAP-001] и находится в `main`; bootstrap
слит через [PR №3][bootstrap-pr]. Разрешение подготовить изменения
по-прежнему не означает их принятие. Исходные ограничения безопасности из
[README](README.md) действуют для всех последующих изменений.

Bootstrap включал только документацию и шаблоны. Стек Django + Wagtail +
PostgreSQL выбран владельцем для дальнейшего проектирования, а требования
первой версии утверждены в [MVP-001][mvp]. Открытые вопросы собраны в
[границах продукта](docs/product-scope.md). Документационные задачи не
изменяют код приложения, зависимости и инфраструктуру без отдельного
согласования.

## Порядок выполнения задачи

1. Создайте Issue с целью, исходным состоянием, полным commit SHA,
   границами изменений, ограничениями и проверяемыми критериями готовности.
   Канонический ID — назначенный GitHub номер Issue в этом репозитории.
2. Согласуйте объём с владельцем. Отделите утверждённые требования от гипотез.
   Неясности и новые продуктовые решения вынесите на согласование.
3. Работайте в выделенной ветке, не в `main`. Если среда закрепляет рабочую
   ветку за сессией, используйте именно её. Не меняйте одни и те же файлы
   параллельно с другим исполнителем без согласования.
4. Подготовьте минимальные изменения в согласованных границах. Свяжите один
   PR с задачей; изменение объёма требует отдельного согласования.
5. Выполните применимые проверки. Укажите точные команды, версии разовых
   инструментов, результаты и причины невыполненных проверок.
6. Зафиксируйте изменения и получите полный SHA командой
   `git rev-parse HEAD`. Представьте PR с отчётом по этому SHA.
7. Запросите техническое ревью и отдельное решение владельца. До решения
   результат имеет статус «предложено / на ревью», а не «принято».
8. Новые коммиты требуют актуального отчёта, повторной проверки изменённой
   части и подтверждения итогового SHA. Старое ревью относится к старому SHA.
9. Слияние выполняется только по явному решению владельца. Не включайте
   автоматическое слияние. Принятие bootstrap, выбор стека и принятие
   [TECH-DESIGN-001][tech-design] не утверждают будущие продуктовые задачи
   и не разрешают реализацию приложения.

Подробные роли и форматы сообщений: [протокол](docs/coordination.md).

## Регистрация и идентификация задач

Используйте форму задачи. [Конфигурация](.github/ISSUE_TEMPLATE/config.yml)
отключает обычный пункт Blank issue в веб-интерфейсе. GitHub сохраняет его
для пользователей с правами Write и выше; API тоже не обеспечивает
обязательность полей формы. Это не глобальный запрет создания пустых задач.

Для задач через API и для пользователей с повышенными правами действуют
те же требования к содержанию и безопасности. До начала работы автор и
ревьюер проверяют полноту задачи и валидность исходного SHA. Неполную
задачу возвращают на уточнение, а не считают согласованной.

В ссылках указывайте номер Issue или полный URL. Заголовок должен описывать
цель; вручную дублировать номер в нём не требуется. GitHub показывает номер
отдельно. Не используйте заголовок или самостоятельно введённый ID вместо
ссылки на Issue.

Именные алиасы, например BOOTSTRAP-001 для Issue #2, назначает владелец.
Перед назначением он проверяет существующие Issues, включая закрытые.
Один алиас относится только к одному Issue; до уточнения конфликтующего
алиаса используйте канонический номер. Для ADR применяется
[идентификация по номеру отдельного Issue](docs/decisions/README.md).

## Ревью и утверждение

Ревью содержит ссылку на PR, полный commit SHA и конкретные замечания или
вывод. Отсутствие замечаний не заменяет решение владельца.

Владелец явно указывает решение и полный SHA в PR: через GitHub review,
если это доступно, либо отдельным комментарием. Автор PR или агент не должен
выдавать собственный отчёт за утверждение владельца. При общей учётной
записи источник сообщения обязательно подписывается.

### Проверка SHA

Форма задачи и Markdown-шаблон PR не проверяют формат или существование
коммита. Автор и ревьюер выполняют проверку явно. Сначала получите объекты
из указанной ветки или PR; если исходный коммит получить нельзя, это блокер,
а не повод подставить текущий `HEAD`.

В Bash определите проверку полного SHA именно объекта-коммита:

```bash
verify_commit_sha() {
  local sha="$1" resolved
  [[ "$sha" =~ ^[0-9a-f]{40}$ ]] || return 1
  resolved=$(git rev-parse --verify "${sha}^{commit}") || return 1
  [[ "$resolved" == "$sha" ]]
}
```

Скопируйте SHA из Issue или отчёта, а не генерируйте замену из своего `HEAD`:

```bash
read -r -p 'Проверяемый полный SHA: ' sha
verify_commit_sha "$sha" || exit 1
```

Ненулевой код означает остановку и исправление ссылки. Для базовой версии
Issue достаточно корректного SHA существующего коммита; она не обязана
совпадать с вершиной PR. Для отчёта и ревью дополнительно сверьте SHA с
текущей вершиной конкретного PR:

```bash
read -r -p 'Номер PR: ' pr_number
[[ "$pr_number" =~ ^[1-9][0-9]*$ ]] || exit 1
git fetch origin "pull/${pr_number}/head" || exit 1
head_sha=$(gh pr view "$pr_number" --json headRefOid --jq .headRefOid) || exit 1
verify_commit_sha "$head_sha" && test "$sha" = "$head_sha" || exit 1
```

Неудача любой команды блокирует согласование. Укажите в отчёте проверенный
SHA и результат сверки. Это ручная проверка, а не встроенная валидация формы.

### Контроль непосредственно перед слиянием

Владелец заново получает текущий SHA PR и сравнивает его с SHA своего
явного решения, используя проверку выше. Если они различаются, слияние
останавливается: требуются актуальные проверки, ревью и новое решение.
Одобрение SHA A не разрешает слияние SHA B.

Для отдельно разрешённого слияния через `gh` дополнительно используйте
`--match-head-commit` с одобренным полным SHA: изменение вершины между
проверкой и запросом должно привести к отказу, а не к слиянию новой версии.
Если клиент не поддерживает этот флаг, остановитесь и согласуйте дальнейшие
действия. Этот документ и обработка ревью не разрешают запуск слияния.

Branch protection, обязательные проверки и CI здесь не настраиваются.
Ручная сверка без атомарной привязки при слиянии, например в веб-интерфейсе,
не исключает гонку обновления ветки и ошибку оператора. Не объявляйте
техническую гарантию там, где действует только правило процесса.

## Проверки документационного PR

Проверьте рабочие и подготовленные изменения:

```bash
git diff --check
git diff --cached --check
```

После коммита сначала обновите базовую ветку. Не продолжайте сравнение,
если получение изменений завершилось ошибкой:

```bash
git fetch origin main || exit 1
git diff --check origin/main...HEAD
git diff --name-status origin/main...HEAD
git rev-parse HEAD
git status --short
```

Трёхточечный diff показывает изменения ветки от общего предка. Он не
заменяет проверку конфликтов или совместимости с новыми изменениями `main`.

Дополнительно проверьте Markdown, существование целей относительных ссылок
и корректность YAML формы задачи и конфигурации шаблонов. Если применяете
разовый валидатор, укажите его версию и команду в PR; это не выбор стека
приложения.

В репозитории есть приложение Django + Wagtail и workflow CI
(`.github/workflows/ci.yml`): проверки Django/Wagtail, миграции и тесты на
PostgreSQL, production-проверки (`check --deploy`, `collectstatic`) и сборка
Docker-образа. Для документационного PR по-прежнему не заявляйте проверки
приложения как выполненные, если они фактически не запускались для вашего
SHA: пишите «не запускалось» с причиной и опирайтесь на фактический статус
CI проверяемого коммита. Чистый Git diff и корректные документы не являются
тестированием продукта. Внешние проверки интеграций указывайте отдельно по
их результатам.

После изменения проверяемых файлов повторите применимые проверки и
обновите SHA отчёта. Не публикуйте необработанные логи с чувствительными
данными.

## Безопасность

- Запрещены секреты, пароли, токены и любые персональные данные, особенно
  реальные данные детей. Не включайте их в файлы, историю Git, Issues,
  Discussion, PR, логи, отчёты, скриншоты и вложения.
- В примерах и проверках используйте только синтетические данные.
  Маскирование реальных данных само по себе не делает их допустимыми.
- Не добавляйте материалы без необходимых прав.
- Удаление данных, изменение production, платные операции и другие
  рискованные действия требуют отдельного явного разрешения владельца.
- При обнаружении секрета остановите публикацию; не цитируйте его повторно.
  Сообщите владельцу без значения секрета для отзыва и безопасного удаления.
